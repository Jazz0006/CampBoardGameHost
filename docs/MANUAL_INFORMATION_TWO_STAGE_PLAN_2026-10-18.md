# 人工信息录入两阶段方案（2026-10-18）

## 产品决策

清理阶段只实施 **第一阶段：完全自由的人工结果录入**。不继续沿用现有 `PairInformationLegalDomain`、Chef/Empath 正确信息计算、Spy/Recluse 登记见证、模型候选 ID 或复杂旧规则引擎，也不趁本轮重建简化版本的合法性引擎。真正的状态感知候选计算是 **清理完成以后** 的独立第二阶段。

### 第一阶段——当前 M1 剩余验收

- MANUAL / AI_ASSISTED：人工为每条需要发布的信息直接指定**最终展示的内容**；可以在信息的格式范围内选择任意值，而不是必须匹配 Host 枚举的所谓合法结果。AI 辅助建议属于可替换草稿。
- 结构输入：数字、真假、角色、角色与两座位声明、无对应角色、选中目标等。合法的**数据结构**仍检查（现有座位、不同的两座位、有效角色标识、接收者、对局身份等）。不能把“无限制”解释为容许无效记录、串局/泄密或过期 AI 响应写入。
- 方桌保留直观人工操作（座位选择、角色选择、信息确认、玩家展示），但**不根据真实角色/中毒/醉酒/Spy/Recluse 等做规则约束或自动真实答案**。信息文字和权威记录来自实际确认的同一值，不能从角色状态回算。
- 原已确认状态/事件日志、原子提交、去重、隐私、局面版本隔离和安全步骤推进照常保留。自动模式权限不能因放开人工输入而扩大。
- 所有人工信息形态迁移后，**删除**旧合法候选、计算、注册解释和专属 UI/测试，不保留长期两套框架。M1c 的自由数字/占卜师真假仅为当前部分成果；Chambermaid、角色与 pair 尚未全面覆盖。

### 第二阶段——完整清理验收后再启动，不得在当前 M1 混入

这是新设计，**不是把旧规则域恢复**。仅用于缩小人工界面建议列表并提升效率，不替代说书人做战略决策；细节以后另行审计和验收。

1. **Pair 信息**（洗衣妇、图书管理员、调查员等）：说书人先选择要向玩家指出的两名座位（如 2、3），然后方桌中央的角色下拉列表按所选座位及本次信息来源状态更新。通常两名固定角色时只展示对应的两个角色选项；涉及可变登记的间谍/隐士，或信息来源醉酒/中毒时，列表允许本局范围内其他可选角色。动态候选展示不等于必须自动写入登记推理事实。
2. **厨师 Chef**：在确定初始阵容时准备对局可能使用的数字界面范围，考虑清醒与失效（醉酒/中毒）场景；显示信息时按当前实际状态提供数字按钮。对失效信息不能无依据声称规则上存在固定最大值：第二阶段需要明确实用 UI 数字范围的定义及极值处理。
3. **共情者 Empath**：在每次即将展示信息时检查当前能力状态与当夜左右邻座，更新允许显示的一个或多个数字按钮，而不是沿用开局缓存；状态或相邻存活玩家变化后重新生成。

**阶段门槛**：只有规则引擎/候选旧实现、AI 旧协议及其所有消费者已按 M1–M5 清理完毕，并且 Session 事实完整性得到证明，才新建第二阶段设计/实现工作；当前阶段不得添加上述候选计算、专项校验、缓存或针对角色的特殊新逻辑。

## 验收示例

- 人工输入原候选列表中不存在的数字、布尔值或两座位角色声明，仍能在结构正确时确认、记录及展示相同内容。
- 提前变更演员真实角色/中毒状态不会擅自改动已确认或正在输入的展示结果。
- 不把用户选择的“3号共情者收到 1”转写成被规则验证过的 TRUE/FALSE 或某个并未明确决定的 Spy/Recluse 登记。
- 第二阶段的 pair 两座位→下拉列表更新，以及 Chef/Empath 动态数字按钮，在本清理阶段明确 **不作为验收要求**。
