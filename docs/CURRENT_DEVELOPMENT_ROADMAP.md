## 新增产品路线：暗月初升（Bad Moon Rising / BMR）——先完整 MANUAL，再扩展规则辅助与 AI（2026-11-02 规划）

**状态：所有者已授权持续实施，第一阶段人工主持代码已接通，待本地/真机验收。** 本路线是在现有 TB 5–15、NGJ 5–6 及已完成 Host UI 重构基础上的**独立新剧本功能线**，不将前面的“AI 不可用/恢复后仍可人工完成对局”优先级标记为已完成。不借 BMR 任务重新启动全仓架构重构。以下五批表保留原实施与验收范围；当前事实以[完整人工主持交付](BMR_MANUAL_GAME_PROGRESS_2026-11-02.md)为准。

### 目标与范围

- **第一阶段目标**：内置完整《暗月初升》剧本（官方 13 镇民、4 外来者、4 爪牙、4 恶魔），支持适当人数（目标 5–15 人）的人工开局、逐夜/逐日主持、全部角色及特殊事件、终局、存档和继续。真人说书人负责 BMR 新增的复杂规则效果与合法裁量，APP 负责准确呈现输入、引导正确唤醒/触发次序、确认实际结算并记录事实。**不依赖 AI API，不能用“手动模式”绕过必需的角色/事件步骤。**
- **第二阶段目标**：在已能完整人工主持的同一 Session 和操作入口上，逐步加入可确定的规则求值及 AI 辅助/自动推荐。按角色逐批审查，不预先建设 BMR AI 开局联合作战、后夜推荐或通用大规则引擎。
- 新剧本和原 TB/NGJ **共享同一 ClocktowerGameSession/ClocktowerSessionState、结构化确认事件、AtomicFile 存档、方桌/座位渲染、日夜 UI 与 D2 信息展示/Next 协议**。不得新增 BMR 专用可写 GameState、独立夜间游标、第二恢复器或长期双套 UI。
- Host 继续负责唯一事实、操作顺序、去重/过期输入/原子提交及已有确定性规则；第一阶段不为 BMR 复杂效果实现泛用自动裁判。真人确认的行动、未致死结果、实际死亡、复活、登记死亡、身份/阵营/醉毒变化和终局，应成为**独立可追溯的已确认事实**，而不是 UI 的临时开关。
- 阵容默认在官方开局规则内随机生成，支持主持核对、重新生成及人工调整；模板品质标准、阵容评分与自动淘汰差阵容属于另一个任务，**不阻塞 BMR MANUAL 完整游戏**。开局仍执行人数与角色构成的必要结构检查。

### 扩展前的生产代码边界（2026-11-02 历史只读核查，以下缺口本次已接入）

- 剧本接入当前只有 `ClocktowerScript.TroubleBrewing / NoGreaterJoy`；内置目录在 `BuiltInClocktowerRulesetCatalog`，入口在 `CampBoardGameHostApp.startClocktowerGame()`，角色展示在 `ClocktowerPresentationRoleCatalog` / `RoleCatalogAdapter`。
- `ClocktowerNightFlow.nightInteractions()` 有 Imp、Mayor、Ravenkeeper、Sage 等专属条件；`ClocktowerHostNightStep` 的行动枚举与完成判断也是 TB/NGJ 取向。要让 BMR 角色按剧本夜序/条件唤醒、正确确认步骤，**复用现有流程入口并在 Session 内扩展**，不可仅加 BMR JSON 即宣布完成。
- `ClocktowerDayFlow.killInDay()`、`finishIfDecided()`、`ClocktowerGameSessionAliveBoundaries` 默认处决导致死亡、玩家死亡不可逆、无存活恶魔即结束；`ClocktowerSessionJson` 限制剧本 ID 且恢复校验假定死亡不可逆。它们是 BMR 的**真实跨剧本结构缺口**，必须集中改正，而不是为 BMR 在 UI 侧设特例。
- `PlayerState` 目前以 `alive` 和单个 `poisoned` 字段表达简化状态；BMR 的公开/登记死亡、复活、来源和期限不同的醉毒需审查并做**最小、可恢复的状态与事件扩展**，不能用大量角色专属永久 Boolean 代替事件。

BMR-A 的代码入口、人工配置/疯子展示身份、存档兼容、开发预览边界及验证预算记录在 [第一步实施方案](BMR_A_IMPLEMENTATION_PLAN_2026-11-02.md)。该阶段 DEBUG 预览是历史检查点，现已由真实 MANUAL 流程取代，不保留并行预览入口。

### 关键能力的最低实现要求

1. **行动与结果分开。** 处决不必导致死亡；攻击可能被保护抵消；一个夜晚可能造成多次死亡。由真人确认实际结果；Session 保留导致该结果的已确认操作及变化。单次原子确认可以包含多条有序结果，不得将多个目标合成一条丢失先后关系的“死亡总数”。
2. **复活与真实/登记生死分开。** 支持教授与沙巴洛斯复活、恢复正确的存活/投票语义；僵怖第一次“死亡”应实际存活但按规则登记为已死，不能实现为先真死再复活。检查死亡、投票资格、提名与终局所有消费者，防止各自猜测生死。
3. **醉酒与中毒有来源和期限。** 水手、旅店老板、侍臣、吟游诗人、普卡等需要不同有效时序；不能直接沿用 TB 投毒者在固定时点解除的假设。效果确认发生时记录在 Session，来源失效、目标死亡、昼夜转换及其他解除条件按需局部处理。
4. **四恶魔输入差异明确。** 珀可主动不攻击并于随后夜晚按顺序选择三次；沙巴洛斯选择两个攻击目标并有复活可能；普卡跨夜毒与延迟死亡；僵怖带有白天死亡条件、第一次登记死亡与后续行动。第一阶段只保证输入完整、真人结算、事实正确；不要以随机目标/默认杀死冒充结算。
5. **非常规触发不等于固定夜序步骤。** 疯子的伪恶魔信息、真实恶魔接收疯子目标，莽夫被他人选择时即时触发，月之子等死亡触发及主谋特殊终局，需要在既有步骤中支持对应条件事件；不得为触发角色无条件增加错误唤醒。
6. **信息私密边界不变。** 说书人可多次预览最后一次将展示的信息；仅显式 Next 记录最后一次实际展示的 Observation。任何玩家全屏信息页不得泄露实际阵营、醉毒来源、疯子真实身份或其他私密 Session 事实。
7. **游戏结束与存档兼容。** BMR 特殊胜负允许真人主持确认，但 Host 不得在僵怖/主谋场景错误自动结束；新增事件/状态有明确编码与恢复语义，旧 v1 TB/NGJ 活动存档仍能恢复。不要用 BMR 特例削弱原剧本已自动处理的确定性结果。

### UI、验证和明确不做

- 沿用已有统一方桌、角色红蓝卡片及死亡/鬼票/醉毒标记，按需要**补充登记死亡/复活相关的说书人私有提示**；优先复用交互组件，不为 25 角色各建一套 Screen。新增少量可复用的“无目标/不攻击”“行动无致死效果”“确认复活”“按顺序多目标”“身份/阵营变更”操作。
- 第一轮先做**8 人珀局端到端**，再逐个打通 8 人沙巴洛斯、普卡、僵怖代表局；特别复核蓄力三击、保护抵消、复活后鬼票、跨夜毒与延迟死、登记死亡/实际存活、主谋特殊结束。随后逐角色覆盖审计；人数变化只补高风险有价值实例，不进行笛卡尔积测试。
- 高价值测试只保护错误生死/胜负/触发、私密信息泄露、事件重复/错误顺序、存档/复活后恢复、无法继续。依实际风险选择验证；代码批次遵守当前精确 SHA Android CI/R2 政策，文档修改不冒称通过 Android 编译或真机。
- **第一阶段明确排除**：BMR 首夜 AI 联合推荐、BMR 后夜 AI、自动解全套死亡保护组合、通用规则/评分/世界枚举引擎、动态 Homebrew 剧本、模板自动评分生成、为规模而增加的全组合测试。保留现有 TB/NGJ AI 三模式与付费调用授权边界。
- **正式编码前复核**每个角色的官方能力原文、夜序和边界情况，尤其僵怖登记死亡的可投票/提名语义、普卡时序、疯子信息、莽夫触发与主谋胜负；以上路线是工程范围和验收合同，不把概略描述当作已实现的详尽官方规则解释。

**执行顺序建议：** BMR-A → BMR-B → BMR-C（先珀端到端）→ BMR-D → BMR-E；只有在人工完整一局可用并验证后，才开始第二阶段 AI 辅助。每批只修改当前实际消费者，替换即删除旧路径，不额外造兼容层。
