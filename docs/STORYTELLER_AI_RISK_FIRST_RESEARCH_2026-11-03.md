# 说书人 AI：风险优先的提示词与专用模型研究（2026-11-03）

> 状态：**总体原则已由所有者确认；下述 Prompt 文字、风险分类、数据协议和训练技术均为待逐项讨论的建议，尚未批准进入生产。**
> 本文为讨论与决策台账，不代表代码已修改或真机/付费模型已验证。当前优先讨论 **现有 Prompt 优化**；专用模型与数据收集留待后续。

## 1. 本次形成的核心决策（已确认）

- 对《血染钟楼》说书人的真实裁量，通常**没有唯一最优解**。很多 A/B 方案各有优点，不应训练模型强行排出绝对名次。
- 核心目标是**发现并排除明显糟糕、可能显著损害玩家体验的方案**（含若干单独合理但**组合后**有害的选择），同时尽量**不误杀合理/有创造性的方案**。
- 对剩余可接受方案允许多样性与一定随机性，而不是长期采用同一「最优」套路；风险判断必须基于当前局势、经验水平、已确认信息和未来不确定性。
- 不把「给酒鬼错误信息」「善恶某方占优」「信息暂时互相冲突」本身标记为不良；要看玩家是否仍有有意义的选择、推理空间和参与感。
- 保留既定职责：**Host/Session 负责确定性事实、合法性、确认与持久化；AI 负责确实存在裁量空间时的体验风险判断与建议**。策略记忆不是真实事实。
- 工作顺序：① 优化当前 Prompt；② 研究专用风险评估模型；③ 训练数据收集和评价体系。按主题逐项讨论，不提前替所有者确定未讨论的细节。

## 2. 2026-11-03 的现有实现核查

代码位置：
- `app/src/main/java/com/codex/campboardgamehost/clocktower/session/InitialJointOpeningDirectV2.kt`：`INSTRUCTIONS` 首夜整局联合规划；`responseSchema` 保持一套方案及 `strategyMemory`，仍要求「**联合选择唯一最合适的首夜整体配置**」「**只输出一套完整可执行的推荐**」。
- `app/src/main/java/com/codex/campboardgamehost/clocktower/session/StorytellerStrategicContinuationV2.kt`：`INSTRUCTIONS` 后续一条当前待裁量决定；要求「**从整局战略评估当前唯一待裁量的决定，直接返回一条语义结果**」。
- `app/src/main/java/com/codex/campboardgamehost/clocktower/session/PersonalDirectOpenAiV1.kt`：`/v1/responses`；每次提交当次 instructions 和严格 JSON Schema；同局可能携带前次 response ID，但不自动继承当次 instructions。
- 首夜输入含展示/真实身份、玩家经验、有无酒鬼、decisionInventory、最近跨局信息；续局输入含最新 Session 状态、已记录声明、历史增量、已有可修订策略记忆及**当前一条** decision。
- **现有 Schema 没有 abstain/uncertain 的可执行响应状态，也没有显式的「多个备选方案及其风险」输出**。首次优化必须遵循单一可执行结果的合同；不要假装仅修改提示词就能安全中止自动决策。
- 现有首夜提示词把独一「最合适」当目标，容易驱动模型过度优化/主动平衡；续局提示词则倾向直接给答案，没有显式的「避免明显负面体验」审查步骤。这是**提示词可改善的假设**，不是已由 A/B 试验证明的缺陷。
- 当前 BMR（暗月初升）路线仍为 **Manual 优先**；此处不把 BMR AI 规划视为已启用。

## 3. 议题一：当前 Prompt 优化（优先讨论，暂不改生产代码）

### 3.1 主原则建议

将「选唯一最优」调整为：

> 在严格遵守 Host 事实、合法裁量边界与历史承诺的前提下，先识别明显可能损害玩家体验的方案或**整套组合**；仅排除有充分理由支持的严重风险方案。允许多个方案同样合理，不必证明所选方案优于全部其他方案。若存在多个可接受方案，选择其中一个有可解释性的方案，并保留风格多样性。不得为了人为维持均衡而强行操纵胜负或填补未发生事实。

重点风险（**拟议审查维度，不是硬性规则或固定评分公式**）：
1. 过早消灭合理推理世界或对抗空间；
2. 让部分玩家持续失去有意义的信息/行动/表达机会；
3. 多条信息相互组合造成非预期的单边锁死；
4. 只为「维持紧张」而过度干预已由玩家行动形成的局势；
5. 与已确认、已公布的事实及历史信息矛盾（事实一致性由 Host 最终把关）；
6. 以高度不确定的未来声明、玩家行为和登记假设作为已发生事实。

审查应同时防止**误拒可接受选择**，尤其不要把酒鬼信息不实、迷惑性或短期优势本身当作风险。

### 3.2 首夜 Prompt（方向已更新：返回三套方案）

**2026-11-03 用户新增明确需求：一次首夜 AI 请求返回三套完整且有实质差异的联合方案，而不是单套。** 优先仍维持一次 API 调用，但**现有严格 JSON Schema 只有单个 openingPlan，不能仅改 Prompt**；实施时需协调 responseSchema、decode、推荐 DTO、候选选择 UI、AI_ASSISTED/AI_AUTOMATIC 采纳链、策略记忆归属和相关高价值测试。以下为讨论中的模型策略步骤：
1. 在内部辨认 Host 确定事实、确实可裁量部分与未来待决部分；
2. 考虑少量具有**实质差异**的整体配置，而非盲目枚举或为所有方案排名；
3. 首先做合法/合同边界检查（Host 仍然是实际权威），再作对整套配置的玩家体验风险检查；
4. 仅排除**明确高风险**的配置；有不确定性时保持谨慎，不能将预测等同事实；
5. 从其余合理配置中选择**三套不同的完整可执行方案**，每套均应独立包含 Drunk/Red Herring/bluffs、information、deferredActions 与相对应的 strategyMemory；优先多样性而不是强制对三个方案排名；
6. `tradeoffSummary` 简要说明避免的主要风险和所选方案的可接受性，不声称全球最优。

### 3.3 后续单决策 Prompt（候选修改方向）

保留 `currentDecision → currentResult` 单条输出，不引入新的角色专用推荐器：
1. 先区分已确认 Host/玩家观测与记忆中的战略猜想；
2. 识别当前确实存在的裁量空间，内部考虑少量合理结果；
3. 先检查是否会产生明显不良的体验、组合信息及历史一致性风险；
4. 若不止一个可接受结果，选其一，无需相互精细排名；不要机械追逐「善恶平衡」；
5. `strategicDirection` 说明具体判断依据、已知事实与重要不确定性；`updatedStrategyMemory` 存关键张力和需警惕的未来风险。

### 3.4 第一轮不要顺手改的事项

- 不修改 Session 事实、规则引擎、UI、GameState、JSON 持久化或三种主持模式。
- 不增加通用 Host 候选世界枚举/评分器；更不让 AI 替 Host 计算确定性规则事实。
- **此前“首轮不修改 JSON Schema / 解析器”的约束已被用户新增的三套方案需求覆盖。** 可在独立生产改动中最小化扩展三套输出与选择接口，但不顺手重建 Host/Rules；先讨论确定合同与模式行为再实施。
- 不以文本 Prompt 假装实现了风险拒绝、人工升级、重试/后备策略。这些需要单独设计返回协议和 UI/自动模式行为。
- 保留两类跨局防重复、事实与私密边界，不在文档/日志里存 API Key 或个人玩家敏感内容。

### 3.5 待讨论的产品取舍

- 是否把「某些方案不够理想」与「明显会伤害体验」区分为不同严重度，并如何定义排除阈值？
- 首夜是否以「整局组合」为唯一筛选对象，还是还要针对一条线索先筛选？
- 三套推荐如何呈现：应为三套**相互独立的完整方案**，而不是三个局部信息选项；辅助模式允许用户选择其中一套，Host 只确认采纳的一套。自动模式的三选一政策还未讨论。
- 如果真实局势无法找到三套足够不同且可接受的方案，如何诚实表达不足并避免硬凑低质量方案？需要在输出协议中明确。
- 自动模式如果候选都很不理想、没有把握，如何人工接管/保留合法默认行为？此项**仅作为后续输出协议变更议题**。
- 评审时首要优化漏掉坏方案（false accept）还是误杀好方案（false reject）？如何兼顾？

## 4. 后续议题：专用模型（暂不实施）

- 目标倾向于 `RiskEvaluator(state, candidate|jointPlan) → acceptable/risky/reject/uncertain + reasons`，**不是**强制为所有方案排出绝对名次。
- 可以先用当前通用模型验证判别任务；后续研究较小的分类模型、LoRA/SFT、带「不分胜负」标签的偏好学习。
- 重大难点是**组合风险**、上下文不足、创意方案的误杀以及不确定性校准。若需独立评估器，不等于立即重建现有 APP 的 AI 模块。
- 模型推理结果仍是建议，Host 负责合法性、最终事实及提交。

## 5. 后续议题：训练数据与 EvidenceLab（暂不实施）

- 训练数据基本单位拟为决策切片：`决策当时可见状态 + 候选动作/整套方案 + 专家风险标签 + 可审计理由`。
- 同一状态下允许多个 `acceptable`，不强制 A/B 分高下；记录明确拒绝理由和标注分歧；保留 `uncertain`。
- 真人记录、专家设计局与合成局结合。先保留独立测试局、对照未微调模型；评价 **坏方案召回率** 与 **合理方案误拒率**，再决定是否值得微调。
- 必须防止未来信息泄漏。若采集实际玩家公开声明、游戏历史、模型建议及人工覆盖，须明确隐私范围、脱敏/留存及授权，不能把调试日志原样搬为训练集。
- 不用简单胜负率作为唯一质量奖励；不把所有规则允许的欺骗信息标为坏方案。

## 7. 2026-11-03 用户追认：三套联合方案与高风险回归案例

### 7.1 已确认产品目标（尚未投入生产）

- 首夜调用返回 **3 套**完整的联合信息方案（不是一套方案中的 3 条单项推荐），希望让辅助模式的 Host 在不同的合理方案间作选择；整体风险优先，3 套之间不要求决出最优。目标是一次 API 返回，不预设三次付费调用。
- 方案必须相互独立且具有真正的配置差异：不能把酒鬼选择、红鲱鱼、恶魔掩饰、条件信息、策略记忆跨方案混用。选择后仅以被采纳的一套作为后夜策略记忆与 Host 事件来源；其他候选不构成已确认事实。
- **实现依赖**：当前 `InitialJointOpeningDirectV2.responseSchema` 是 `openingPlan` + `strategyMemory` 的单方案顶层结构；直接把 Prompt 改成“三套”会触发 decode/验证失败。生产实施时必须先明确新版本 Schema、严格验证、采纳 UI、恢复和续局记忆接口。原有生产不变。
- **开放问题**：若不满 3 套安全方案如何返回，3 套的去重标准，自动模式如何择一，后续夜晚是否也返回 3 条推荐，全部后续另议；不得为凑数量输出风险方案。

### 7.2 真实历史案例：8 人 E03_R1（高风险分析候选，非已证实唯一锁死）

- 已检索到独立档案 `E03_R1.plan.json`。座位依次：1 调查员、2 厨师、3 占卜师、4 隐士、5 共情者、6 间谍、7 洗衣妇、8 小恶魔。无酒鬼。
- 首夜方案：洗衣妇报“2/4 中有厨师”；厨师 0；共情者 1（邻座 4/6）；调查员报“4/6 中有间谍”；占卜师询问对象未发生，保持 DEFERRED；红鲱鱼为 2。
- 风险机制：同一区域重复出现的调查员/共情者证据，加上厨师 0 与洗衣妇的身份佐证，可能形成不利于邪恶的交叉验证链。但隐士/间谍注册歧义、玩家假声明等仍使绝对锁死结论不成立；原始 strategyMemory 明言 “Spy and Recluse open to discussion”，因此必须将其列作**待评估组合风险样本**，不能冒称已正式被人工标注 BAD_TOO_STRONG。

### 7.3 另一历史案例：7 人首夜 BAD_TOO_STRONG（与八人案例易混淆）

- 2026-09 既往讨论过的 7 人布局：1 洗衣妇、2 厨师、3 共情者、4 占卜师、5 调查员、6 猩红女巫、7 小恶魔；存在洗衣妇与厨师/共情者的相互确证、厨师数字 1、共情者数字 0、调查员涉及爪牙的配对信息。
- 在该实验的**公开好人信息假设**下，旧分析报告邪恶座位拓扑候选从约 30 缩至 4；移除厨师或共情者单条证据后回升至约 10，并在讨论中标为 `BAD_TOO_STRONG`。这些数是历史实验条件下的**结构候选数量**，不是玩家主观猜测的概率，也不表示实际游戏必然锁死。
- 值得复用的是已有旧实验方法学：联合信息交叉验证、留一条信息再测（leave-one-out）、替代邪恶位置/身份解释的可理解程度；**不恢复**已废弃的旧复杂 Host 规则评分引擎。将两个案例作为新旧 Prompt 的回归/反例比较数据。

### 7.4 待讨论的下一问题

- **把“返回三套”落实到产品协议，并确定三套必须如何不同，以及整套方案如何进行风险筛选。** 此项确认之后再形成生产 Prompt、Schema/DTO/UI 的最小实施包；继续使用独立对照样本验证“坏组合”是否被识别，而不是仅靠 Prompt 的自我说明。

- \`PersonalDirectOpenAiV1.kt\` 每次向 \`/v1/responses\` 传 \`instructions\` 与 \`strict: true\` JSON Schema；如保留前次 \`response_id\`，本次 instructions 仍重新传入。代码中 HTTP \`readTimeout=90000\` 毫秒；未看到显式输出 token 上限。三候选将增加输出规模与推理负担，必须验证限时、截断和实际收费。
- \`ClocktowerJointOpeningReviewScreen.kt\` 与 \`ClocktowerOpeningDraft.kt\` 当前仅处理单一首夜选择；\`ClocktowerSingleRecommendationChoiceUi.kt\` 对建议 \`.take(1)\`；\`ClocktowerAiConversation.kt\` 的 \`PendingCurrentStepAdvice\`、\`strategicPolicyCursor\`、\`canonicalConversationResponseId\` 亦只绑定一条待采纳结果。不能只改 Prompt/Schema。
- 保留现有首夜酒鬼真正提交、后夜实际信息展示才确认、请求版本/ID/Session 前缀校验、过期回复丢弃的机制；未选中方案没有 Session 事实效力。红鲱鱼的 Host 侧实际善良且非隐士检查继续保留。实施时需进一步确认 Demon bluff 的“未在场善良身份”约束在最终确认链中的规则覆盖，不能只信 Prompt。
- BMR 的 AI 仍不在这轮范围内；已实现的 BMR MANUAL 不应被改动。

### 8.2 最重要的新思想：候选的「反例 / 替代世界证人」检查

把“避免信息太强”改成有明确问题的短流程，仍由 LLM 在**内部**完成，不需要输出冗长 chain-of-thought：

1. **冻结事实/边界**：列明真实阵容、展示角色、已确认并实际发出的信息、各项尚未决定的内容。区分规则强制结果与真实裁量；酒鬼/中毒、登记仅按真实有效条件允许，绝不人为更改不可变信息。
2. **生成少量不同整体候选**：优先从可裁量的 Drunk、pair 信息、Red Herring、Demon bluffs、合法登记及条件意图中形成具有不同信息分布/掩饰路径的完整候选。不要通过改写 Chef/Empath 等必然数值伪造差异。
3. **联合信息图审查**：按线索列出其涉及的座位/身份/邻接限制，查找多个彼此独立的来源共同指向某些座位的链条；检查对某条线索暂时不公开时，推理闭环是否仍成立。不是把各线索的强弱分数相加。
4. **两种公开情境压力测试**：情境 S1 假设健康善良玩家较积极、真实地公开身份与信息，是有意苛刻的压力测试；情境 S2 允许邪恶玩家真实地进行假身份/假线索声明、善良玩家沉默或质疑，并考虑新手能否完成。这两种是假设，**玩家声明不等于 Host 认证事实**。
5. **反证尝试**：从善良玩家在 S1/S2 下所见的声明集合出发，尝试构造至少一至两个规则允许、沟通上能理解的“不同恶魔或爪牙位置的替代世界”，并说明普通邪恶玩家是否能用合法 bluffs 维持它们。找不到不等于数学证明不存在；必须指出原因和依赖条件，不能编造强行成立的世界。
6. **概念性 leave-one-out**：如果疑似锁死，分别暂时移走一条尚未实际公开的信息，判断是否出现合理替代解释。若单独各条线索均合理、叠加后出现强收缩，就是重点组合风险。此处是 LLM 的定性反事实检查，**不能假装做了穷举精确计数**。
7. **宽容判断与选择**：只有当强风险基于稳健、合理的玩家行为假设成立，并且没有足够可理解的对抗解释时，才排除候选。不能把错误信息、短暂优势、混乱、创造性玩法本身认作有害；不确定时保留或标为需要主持人评估。返回最多三套真正有差异的方案，允许 0/1/2 套，不排名。

**保留的认识论边界**：旧研究首次把 \`"I am Empath and got 0"\` 错当 \`ShownRoleAt AND NumericResult\` 的 Host 事实，导致错误锁死；后来纠正为 \`speaker evil OR (真实该展示身份 AND 信息为真)\` 的健康公开阶段假设。新 Prompt 不能重复此错误；上述声明逻辑只是分析指导，不是新生产规则引擎或精确推断公式。

### 8.3 八人 E03_R1：先验证有没有真实锁死，而非预设失败

真实 1 Investigator、2 Chef、3 Fortune Teller、4 Recluse、5 Empath、6 Spy、7 Washerwoman、8 Imp，无 Drunk。现有推荐：WW 2/4 厨师、Chef 0、Empath 1（邻居 4/6）、Investigator 4/6 间谍；FT 查询未发生所以 DEFERRED；原 Red Herring 2。

- 组合可疑处：Empath 1 与 Investigator 对 4/6 的配对形成重合关注；WW 的 2/4 又将 4 牵入身份认证，Chef 0 从全桌角度给附加约束。
- 不能直接认定 6/8 已锁定：4 Recluse 可按相应检测登记成邪恶/爪牙，6 Spy 可按能力登记为善良；各次登记依实际规则与说书人裁量而不是统一全局身份。恶人可伪报角色/数字，善人可能不公开；对 4/6 的重复指向也未必比换配对更坏。
- 样例比较时固定 roster/noDrunk/待决 FT，分别让候选改变 WW/Investigator 的合法 pair、合法登记选择及 bluffs，再审查“真实健康公开压力测试”和“混合/诈称”两个情景是否存在可理解的邪恶反解释。**必须报告替代世界的解释或无法构造的具体前提**，而非只输出“信息过强”。
- 结论：此例标记 **组合风险待确认 / possible false-positive trap**；不是已经验证的 BAD_TOO_STRONG 金标准。模型若未经分析一票否决此真实方案，属于可能误拒。

### 8.4 七人 pair-rich：示范真实坏组合的审查路径

1 Washerwoman、2 Chef、3 Empath、4 Fortune Teller、5 Investigator、6 Scarlet Woman、7 Imp。健康首夜且无特殊登记干扰时，6 与 7 相邻使 **Chef=1**；3 的邻座 2/4 为好人，使 **Empath=0**。在此阵容与状态下这些数值本身不是可供 AI 随意修改的平衡旋钮。

历史 \`cal-pair-rich-adjacent-evil\` 的特定公开假设和选定信息签名曾出现邪恶阵容拓扑由约 30 种缩至 4 种；去掉某条交叉佐证后可回到约 10 种。这些是**旧条件模型下的结构候选数，而非当前现场复算、不是概率，更不是无条件准确的最终标签**。原健康公开语义修正前的过度塌缩报告不能作为基线；正式训练/校准标签仍需人工确认。

该样例要求模型对 WW/Investigator 的合法二人配对进行组合审查，找出哪些 pair 让 Chef 1、Empath 0 的事实与身份声称形成连锁确定性；用留一条信息的定性反事实验证，而不是把某条“好人的真信息”本身判坏。若所有合法结果都强，则允许候选不足三套并交给主持人，而不是产生错误 Chef/Empath 数字。

### 8.5 首夜 INSTRUCTIONS 改写核心段落（不是完整生产替换稿）

> 你的目标不是寻找唯一最佳方案，也不是尽量平衡双方胜率。先构造少量合法、完整、具有实质不同信息路线的联合首夜方案。对每套方案，模拟健康善良玩家积极公开的压力情境，以及存在邪恶假声明、质疑和信息不公开的实际情境。将公开声明与 Host 已确定事实严格区分。
>
> 找出来自不同玩家的信息是否相互确认，尤其是某个座位反复出现在身份、邻座、阵营和相邻邪恶计数的证据链中。尝试从这些声明出发，提出普通邪恶玩家能够理解、规则上允许的不同邪恶阵容解释。若候选看似使邪恶失去合理辩护空间，逐条考虑不公开某一尚未发出的线索后这种结论是否仍成立；检查 Spy/Recluse 登记和 Drunk/中毒等实际有效例外，而非假定它们总能救场。
>
> 只有在有充分具体依据时排除明显有害的联合方案。没有找到反解释不是数学证明；不确定的局面不可简单当成坏方案。错误信息、冲突、局部优势、离奇但可玩方案不自动构成风险。不可更改规则强制的真实结果，不可预言未来玩家目标。至多返回三套互不依赖的完整方案；若只有两套、一套或没有足够合理的方案，如实返回，不要补齐数量、不强制排名。每套独立包含自身 strategyMemory。只输出符合严格合同的简洁结构化结果，不输出内部逐步推理。

**建议保留旧 Prompt** 的实际/展示身份、信息/行动清单完整覆盖、FT DEFERRED、Drunk/Red Herring/bluffs 约束、严格 identity 与响应格式等条款。不要把该段孤立拼到旧的“唯一最合适/只返回一套”指令后面，必须整体消除矛盾。

### 8.7 后续决策与完整采纳：不同于首夜的三包预测

\`StorytellerStrategicContinuationV2\` 每次收到 **一个当前真实 Host 决策**，产生 \`choices[0..3]\`；每个 choice 含 \`decisionId\`、完整当前语义结果、**自身** \`updatedStrategyMemory\` 和简短风险理由。顶层仍绑定同一 Host revision、game log prefix 和原先策略版本，三个候选不共享未来意图。

- AI_ASSISTED 先选择当前备选之一，再逐步预览/确认实际发布的信息；只有实际采纳且与已确认 Observation 一致时，推进该选项记忆与响应 anchor。
- AI_AUTOMATIC 若多个可接受且无须排序的选项，待讨论**中立稳定选择**（例如结合游戏标识/当前决策 ID 的确定性选择）而非默认为数组第一项代表“最好”。若 0 个可用候选，停在人工可处理入口；**不强行创造数据**。
- \`previous_response_id\` 的链上对话可能包含所有未选中首夜候选；续局必须明确传 **selectedOptionId + 被采纳的策略记忆 + Host 已确认事实**，不得因为模型看过其他方案就把它们当成历史承诺。是否保留相同链 anchor 需要专门验证。
- 辅助/自动模式、UI 和恢复只能引用**选中的、通过当前版本与显示域验证**的建议。无持久第二游戏对象或额外 Host 候选缓存。

### 8.8 单次 API 三方案的成本、延迟和验证建议

- 可行性：Responses + strict JSON Schema 完全可以在一次请求的输出中容纳一个小数组；**一次调用不等于三个方案只付一套的 token 费用**。输入 roster/历史只发送一次；输出完整 \`information\`、\`strategyMemory\` 等会随有效候选数大致增长，且内部审查推理成本可能显著增加。
- 建议**不要求先显式输出全部内部候选/详细淘汰记录**。Prompt 内要求有限候选、正反解释、leave-one-out 的简洁思考；最终每套仅输出短的风险摘要和必要合同字段。否则会显著增加输出、截断风险和说书人 UI 噪声。
- 生产运输当前 read timeout 为 **90 秒**，但尚无新方案实际 latency 证据；不得推断三套一定小于此限或声称具体新价格。付费实验仍须单独授权。测量输入/输出/推理 token、响应延迟 p50/p95、HTTP/incomplete/JSON/Host validation 比例、每次有效选项数、三选一实际质量。
- 对照基准：同一阵容、同样模型/参数，比较现有单套旧 Prompt、只改 Risk-First 的单套候选、Risk-First 三套候选。至少包含 E03_R1（防误杀）、七人 pair-rich（识别坏组合）、低信息两来源局（防过度谨慎）、Drunk、Spy/Recluse、FT DEFERRED、候选不足 3、策略记忆后续一致性。**旧实验的 30→4 不作为必须重现的硬阈值**。
- 产品评价指标：模型能否**明确指出发生交叉确认的两三条信息**，能否给出规则有效的替代世界或说明失败假设，是否把邪恶假声明误当不可能，是否更改无裁量的真实数值，是否误拒合理创造性方案，以及每套最终是否能经过 Host 的完整采纳流程。

### 8.9 待所有者后续确认的设计点

1. 风险摘要保留多长，是否展示主持人可选风险标记；\`REVIEW_ADVISED\` 是否保留为候选。
2. AI_AUTOMATIC 的中立选取办法，以及有效候选为零时的人工接管行为。
3. 新 v3 合同处理“其中一个候选格式合法但语义非法”时，是逐项丢弃还是整包失败。
4. 什么算实质差异：是否要求至少一个**玩家接收的信息或关键 Drunk/登记**不同，bluffs 单独变化是否足够。
5. 什么时候进行真实 API 试验、预算与具体模型参数。**本轮不进行付费调用、生产 Prompt/Schema/解析/UI 改动。**

## 9. 2026-11-03 所有者反馈：两案例人工校准与一套/三套策略（覆盖前文尚未批准的建议）

> **决策状态**：本节记录所有者本轮明确的实际体验判断，优先于第 7/8 节中的假设性风险归类及“三套必须成为默认生产方案”的推断。保留第 8 节为研究过程，不能将讨论草案误标为既定实施合同。仍未修改生产 AI。

### 9.1 八人 E03_R1：所有者判定可接受，不应排除

原阵容与首夜信息不变：1 Investigator、2 Chef、3 Fortune Teller、4 Recluse、5 Empath、6 Spy、7 Washerwoman、8 Imp；WW 2/4 厨师、Chef 0、Empath 1（邻座 4/6）、Investigator 4/6 间谍、FT 未选目标。

- 洗衣妇与厨师的身份声明可互相增强可信度，但其他玩家仍可怀疑二人合谋：**声明交叉佐证 ≠ 已被 Host 认证的身份真相**。
- 调查员/共情者指向 4/6 的结构，仍有 4 号隐士按合法检测登记的解释；6/8 邪恶阵营可构造不止一种可说服人的假世界。
- **所有者判断：这个整体方案不存在明显体验问题，Risk-First 不应淘汰。** 它应作为防止 false reject 的正面样本，而不再标“待评估过强风险”的默认负样本；这是主观体验标签，不代表所有可行世界的数学证明。
- Prompt 的评价重点应是能否提出**具体、普通新手可实行**的邪恶辩护路径，不能只因角色线索重叠就否决。

### 9.2 七人 pair-rich：所有者判定高风险，必须注意真实配置下无酒鬼

固定七人示例：1 Washerwoman、2 Chef、3 Empath、4 Fortune Teller、5 Investigator、6 Scarlet Woman、7 Imp。五镇民、一爪牙、一恶魔，**标准七人 TB 默认 0 外来者；此真实阵容没有 Drunk 或 Poisoner**。Chef 1（6/7 邪恶相邻）与 Empath 0（邻居 2/4 善良）在正常运作下均是规则结果，不能为“平衡”而改写。

- 所有者给出的风险因果链：Empath 0 使 2 厨师和 4 占卜师的公开声明更可信；WW 若将厨师身份线索指向 2，则进一步加强 2 的可信度；随之 Chef 1 的邻接约束格外有杀伤力；Investigator 对爪牙的真实线索进一步指向 6，随后 Fortune Teller 的后续合法查询可能进一步收窄，邪恶 6/7 新手玩家可能很难维系合理假故事。
- **所有者判断：这是应避免的组合信息状态**（BAD_TOO_STRONG 方向）。实际是否唯一锁定仍依赖 WW/Investigator 具体 pair、哪些人公开/被相信，以及 FT 尚未发生的目标。不能把 FT 的未来结果当首夜已确认事实，也不能将旧世界数量误读为当前真实概率。
- 用户提出“通过酒鬼并配合 Demon bluffs 打断验证链”的思路，在**允许酒鬼的另一个合法 setup** 中是可取的联合决策策略；但在**这七个具体身份已固定**的局中，Prompt 不允许凭空新增 Drunk。若 TB 需要引入 Drunk，通常需开局存在额外 Outsider 配额（如 Baron [+2 Outsiders]、取代两镇民）；这会改变原五镇民+Scarlet Woman 组合，不能保留其余身份不变只加一个 Drunk。
- **重要的架构新发现**：区分“当前 setup 产生的先天风险（需在开局/模板层评估）”与“固定 setup 内 AI 可裁量的信息组合风险（首夜 Prompt 可以规避）”。当已定阵容几乎没有救场的合法裁量时，模型应如实说明限制，尽力给安全方案或交人工，而非制造违法误导信息。这个结论不授权本轮实现 setup 评分器。

### 9.3 Risk-First 语义：不差的方案，不是风险最小或最佳方案

- 目标是**至少返回一套可接受方案**，不是把所有合法组合做优劣排序，也不追求“最低风险”或“双方实力永远均等”。
- **一套或三套都被所有者明确认为可接受，各有成本与体验收益；方案数量尚未定稿**。不得继续写成“三套固定已批准”。有两条独立、可比较的实施路线：
  - **路线 A：Risk-First × 单套完整输出**。可先只修改 Prompt 与人工评估流程，复用现有单 \`openingPlan\` Schema/解析/UI/后续 memory 采纳链。核心验证模型能否淘汰明显坏组合、不误杀 E03_R1。这是最快/最低成本的第一步。
  - **路线 B：Risk-First × 最多三套独立完整输出**。在相同策略基础上增加 response Schema、解析 DTO、候选 UI、自动模式选取、每选项记忆与过期响应治理。一次 API 调用，若合理方案不足三套无需凑数。
- 待后续讨论是否需要先走 A 验证、再走 B，或直接实现 B。**不能以“返回三套”取代“Risk-First 检验是否真的有效”的主要目标。**
- 对外输出应简短说明“为什么仍合理 / 哪些组合需要留意”，并重视充分的邪恶辩护空间和善良的有效推理空间；不要声称通过数字世界计数给出绝对好坏证明。

### 9.4 新的评估样本角色（以所有者校准为准）

| 样例 | 人工目标标签 | 最重要的检验 |
| --- | --- | --- |
| 8 人 E03_R1 | ACCEPTABLE（所有者确认） | 多条信息重合仍存在可理解的邪恶假世界；不得误拒 |
| 7 人 pair-rich、特定互相确认信息 | BAD_TOO_STRONG（所有者判断；视具体信息签名） | 识别可信度级联和新手邪恶辩护困难，且不改写确定性数字 |
| 7 人相同固定阵容无 Drunk | NO_DRUNK_DISCRETION（机械约束） | Prompt 不能凭空选择 Drunk；必要时提出 setup 阶段调整而不是伪造游戏事实 |
| 低信息两来源局 | 待人工确认 | 防止过度维护邪恶而剥夺善良有效推理 |

**当前明确的不实施项**：不修改生产 Prompt/DTO/Schema/UI，不重建旧评分/可能世界引擎，不进行付费 API 调用；PR 保持 Draft。下一次先比较单套/三套两个产品方案的实际收益，再冻结合同和 Prompt。

### 10.3 无论怎样提供线索都难以隐藏：当前证据与下一步

**本次不能证明 50 套中存在任何“所有合法线索都不合理”的模板，也不能证明不存在。** 当前是**角色池静态审计**，而不是对所有座位、所有合法信息配对、玩家行为、登记、酒鬼、红鲱鱼和善恶伪装的穷举。不能把模板角色集合等同于固定数字：Chef/Empath 数值依赖具体座位；Virgin/Slayer/Undertaker/Ravenkeeper 的确认效果还依赖未来真实行动。即使所有健康好人公开，邪恶玩家仍能提出假声明并使用三项合法 Demon bluffs。

推荐将 \`003\`、\`029\`、\`032\` 标记为**优先研究（不是坏模板）**：
1. 针对每一套，先选出能导致 Chef/Empath 真数字强约束、或多阶段角色确认高度相关的 **具体座位排列与真实行动情境**；
2. 区分必然真实结果、可裁量信息和不可预言的后夜触发；对合法可调选项尝试不同策略；
3. 问“是否至少存在一条对普通新手邪恶玩家可信、可沟通、合法的辩护路径”，并说明其所需 bluffs 和公开假设；
4. 只有对明确的局面/行为假设反复无解，才考虑调整对应模板；不因静态高信息密度自动删除或建立新的全仓评分引擎。

**结论**：历史 BAD_TOO_STRONG 的五首夜信息角色极端阵容已被当前模板池排除；目前应重点研究 **少量首夜线索 + 后夜/公开角色验证导致的可信度级联**，而不是只检查首夜信息角色数量。现有 \`SetupDiversitySelector\` 只负责多局阵容多样性，不是局面风险筛选器；这项任务独立于 Risk-First 当前首夜 Prompt 迭代。
