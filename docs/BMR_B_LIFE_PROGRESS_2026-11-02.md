# BMR-B 生死基础进展与人工审核点

状态：B 批的第一段基础实现，不是完整 B 批，也不是完整 BMR 可玩交付。用户已授权持续推进完整人工对局，遇到需要人工审核的不确定问题时停下来报告。

## 本段已接入的实际消费者

- `PlayerState` 保留实际 `alive`，增加默认 false 的 `registersAsDead`；公共生死统一由 `publiclyAlive` 读取。没有 BMR 第二个 GameState。
- `Execution.causedDeath` 区分处决发生与处决致死；`Revival` 与 `DeathRegistration` 是唯一 Session 确认的结构化事实。登记死亡只用于僵怖首次表面死亡，不能用“先杀死再复活”模拟，也不提供任意登记切换开关。
- 现有提名与投票资格、投票门槛、鬼票来源、方桌生死和死亡轮次读取这些事实。复活后允许再次死亡；复活前用过的鬼票不永久锁死这个座位。
- 已确认死亡/处决记录不再一律要求最终玩家仍死亡；活动局加载使用当前状态，并从确认事实恢复投票站位和必要生死上下文，不重演角色能力。
- 记录页包含复活和登记死亡；未致死处决的详情明确说明没有造成死亡。送葬者的唤醒检查要求真正有处决死亡，不把处决死者算作新死亡。
- BMR 开局校验只在创建时使用，不在恢复中局时强制初始角色构成或初始阵营。TB/NGJ 的现有确定性结算继续保留。

## 活动局文件兼容

仍为现有单个活动局文件、原 AtomicFile 保存入口与 Session JSON v1，无新存档槽、初始快照、界面游标、回放或恢复框架。

- 旧存档没有 `registeredDead` 时默认 false，没有 Execution 的 `died` 时保留旧的致死语义。
- 新字段仅在需要表达非默认情况时写入；新增生死事实通过现有 actions 序列保存。
- 重复确认同一个复活/登记死亡 actionId 是幂等操作，不产生第二条记录。

## 验证范围

现有 Session 和活动局定向回归已通过。新增两项重要行为回归：复活→再死→再次鬼票与序列化恢复；僵怖实际存活/登记死亡和处决未死不会在恢复时变成实际死亡。没有人数×模式、像素或几何测试。

后续醉毒来源/期限、能力恢复、角色操作、特殊终局尚未实现，A 的首夜预览仍不能推进；这些都不能仅凭本段测试通过宣布完成。

## 普卡自毒：用户裁定已落实（2026-11-02）

用户明确裁定：普卡选择自己时，自身持续中毒；上夜旧目标解除中毒且不会因此死亡；此后普卡仍每晚选择，但选择不产生效果。这是项目已确认规则，不声称官方角色页直接说明了该边界。

- 新增 `PukkaChoice` 记录真实选择与是否施毒，`PukkaPoisonEnded` 记录解毒。两者沿用唯一 actions 时间线；不是第二份普卡状态。
- Session 在一次现有原子确认内记录自选、施毒及旧目标解毒。以已确认事实投影当前中毒，源死亡或身份离开时结束毒效；疯子假扮普卡不能调用真实普卡结算。
- 自毒之后仍允许选择，记录 `poisonApplied=false`，不向新目标施毒或误杀旧目标。重复确认幂等、过期确认拒绝；保存失败回滚整个确认。
- 记录页只显示选择和实际生死，隐藏解毒维护事件。
- JSON 仍为 v1，新增类型只进入已有 actions。旧 TB/NGJ 与现有 BMR 开局/生死存档没有这些事实，无新必填字段、初始快照、UI 游标或独立恢复入口。
- 普卡普通延迟死亡、醉酒暂停/恢复以及完整夜间 UI 尚未接通；BMR 仍是不可推进的开发预览，不能把本段描述成完整普卡/完整游戏支持。没有引入尚无消费者的通用醉毒/能力框架。

## 普卡连续同目标：用户裁定已落实（2026-11-02）

用户确认：连续两夜选择同一名非自身玩家时，先结算上夜死亡尝试，保留本夜的新毒，下一夜再次结算；本夜受保护未死也保持新毒。`PukkaPoisonEnded` 因而引用具体的 `choiceActionId`，不会按座位把新旧两次毒一起清除。

延迟死亡与解除旧毒由一次 Session 原子确认完成，真人确认实际死亡/保护结果。没有新的选择（例如被驱魔）也能结算旧毒。死者不能再次死亡；重复确认不新增事实且必须符合已确认结果。完整醉酒暂停/恢复与夜间入口仍在后续批次。
