## 1. 产品目标与不可改变的边界

- 两项现行业务职责：**Host Core** 和 **现有 AI 推荐**。Host 在没有 AI/人工说书人帮忙决定流程的情况下，能够确定剧本、轮次和当前事实所规定的**下一可执行步骤**，以及唯一确定的机械结果。玩家作出的选择仍必须由玩家输入；规则确有裁量空间时由 AI 或人工说书人选择，不允许 Host 随意编造。
- 只有 **一个可写 Session / GameState**：座位、实际/展示身份、阵营、醉毒/保护/生死、角色变化、阶段、玩家操作、单一顺序事件与实际公布信息。UI、AI、复盘、对局恢复、读模型均不得成为第二事实权威。
- Script 定义固定夜序、角色和必要剧本特例；Host 从 **Script + 当前 Session + 有序已确认事件 + 最多一个待提交操作** 得到当前步骤。没有第二套可写游戏状态、通用世界枚举、候选合法域、评分或隐式 UI 裁定。
- **确定性规则由 Host 计算、执行并验证**，包括夜间条件唤醒/跳过、攻击是否致死、保护/中毒时间效力、死亡触发、角色继任、白天提名投票、胜负及无歧义真实线索。只有规则真正存在多个许可结果，才请求 AI/人工裁量；保留必要狭窄的结构/规则边界检查，禁止恢复旧通用 veto 引擎。
- **真实已经告知玩家的信息不可静默撤销**：记录实际数字、布尔、身份、配对、接收者、时点、公开性，即便真实说书人误播；正常状态计算不能伪造“实际已告知”。
- **死亡机械生效和黎明公开是不同的时点**：游戏内部及时更新生死并影响后续动作，公开视图在 Dawn 之前不得泄漏。
- 现行两内置剧本 **Trouble Brewing（5–15 人）与 No Greater Joy（5–6 人）** 必须继续可玩；开局角色阵容防重复与同一玩家连续角色轮换两项均保留。未来自定义/Homebrew/动态剧本非当前要求；可删除其额外复杂性，但必须保留两内置剧本及所需解析。
- **保护现有 AI 整链**：首夜全局联合规划、后夜增量、提示词/API/解析、战略记忆、MANUAL/AI_ASSISTED/AI_AUTOMATIC、预选与逐项应用。不得为旧 Host 合法域或候选接口的保留牺牲最小 Host，也不得删除实际 AI 功能。API 付费实验须另行明确批准。
- Android CampHost 与以后 WebHost/EvidenceLab 只需共享状态和事件**语义合同**，不复制 Android UI 或旧存档/恢复技术；不可为了未来扩展先建设庞大通用引擎。

## 2. 单步暂存与安全恢复：已定稿

统一协议，覆盖夜间目标、私密信息步骤、白天关键确认和昼夜切换：

1. 第 n 步操作界面可编辑草稿。点击“下一步”后，把已选操作保留为 Session 内**唯一 pendingOperation**，计算并显示下一步骤 n+1；此时前一步尚未变成不可改的正式事件。
2. 在 n+1 **实际开始执行之前**（唤醒/对玩家展示私密信息、下一个玩家行动确认、正式公开或其他不可逆现实效果的边界），**一次原子事务**提交 pending n：正式事件、对应真实 GameState 变化、版本/步骤进度一致落盘，再开始 n+1。下一步只是显示，不等于已经执行。
3. 如果 n+1 尚未实际开始，允许“上一步”仅退回 n 的 pending 并修改、重算预览和后续步骤；**最多后退一项，不允许连续撤回任意历史**。错误输入（恶魔本想袭击 6 而误点 3）不是两次实际选择，最终正式历史只应留下攻击 6。若 n+1 已实际执行或公布信息，不得用普通上一步修改 n；真正误播另设显式事实纠正。
4. 暂存的机械影响可经**纯计算临时投影**生成 n+1（例如预期死亡影响后续唤醒），不允许写入第二份 GameState。暂存更改使依赖它的 AI 预测/响应失效（版本/指纹）；正式状态与顺序事实未提交前，不得错误当成已确认的 AI 历史。
5. Session 正式提交与持久化须原子一致，不能出现“GameState 已变，行动/观察未落盘”或反过来的半提交；写盘包括当前唯一 pending 与稳定步骤身份。恢复优先重建**安全可继续的步骤**：若 pending 已保存，则可恢复 n+1 仍允许退回 n；若未安全落盘则从上一可靠操作重新确认。不要承诺逐像素恢复。
6. 步骤身份不能只用会因死亡而变化的列表索引；稳定地绑定对局/日夜/角色或触发事件/本轮出现序号。已完成步骤不能因动态重排重复执行。
7. 夜末“确认进入白天”是最后待提交事件与阶段切换的安全边界，**不再自由勾选实际死者/是否保留中毒/任意继任者**。死亡、能力失效和确定继任在原本触发的夜间步骤生效，黎明只宣布应公布的事实。
8. 严格区分**说书人录入纠错**（pending 未提交，直接修改）与**现实中已经发生的错误/误播**（正式历史须追加显式记录，不能覆写）。实现只允许最近 pending 的更改，不建设泛用 Undo/Redo、事件回滚框架或 EventStore。
9. 若显示步骤 n+1 前就发生不可逆的自动副作用，必须先提交 n；不要用“已经呈现 UI”替代真实提交边界。崩溃后绝不自动再次公开或再次执行已记录步骤。

## 3. 整局执行合同

开局：选内置剧本、5–15/NGJ 5–6、人数配置与剧本修正、选阵容/座位/真实及展示身份、酒鬼、必要红鲱鱼/恶魔掩饰。两类跨局多样性保留；首夜 AI 可提前规划但不能以建议充当事件。

第一夜：Host 根据首夜剧本顺序和当前身份生成开场邪恶信息、角色动作/私密信息；酒鬼按展示身份安排体验但不拥有镇民能力；无需唤醒时不额外要求人或 AI 判断。5–6 人与 7+ 人开场信息差异由剧本/人数决定。

后续夜晚：固定剧本夜序 + 玩家真实/展示身份 + 当前当夜有效能力 + **有序事实** 推出可执行动作。死亡、保护、投毒、失效、恶魔继任必须影响发生之后的角色，但不能按最终状态倒推修改之前已发生的信息；守鸦人/贤者是事件触发步骤，不能只靠当前存活角色集合过滤。间谍正常步骤展示已有方桌，不重建特殊魔典页面。

黎明：只公开已经确定的夜间死亡、办理确实在得知死亡时触发的事件，隐去不应公开的身份/毒/保护等事实。将机械死亡时点与玩家获知死亡时点分开。

白天：自由讨论由人主持进度，但真实提名、投票、鬼票、最高票、处女触发处决、杀手行动、艺术家问答、白天正式处决和胜负判断共用一个 Session 事件与结算机制；Host 计算唯一结果，不把实际自由裁量和技术验证混为一谈。必要玩家输入仍由玩家作出。

循环：每个正式机械变更后检查游戏终结与特殊继续条件，否则继续下一夜；不能维护日夜两个独立状态机。

## 4. 角色覆盖合同与非穷举组合矩阵

P0 必须依据两内置剧本官方/现存角色定义，制作**每个实际角色**“触发条件、必要玩家输入、确定效果、非唯一裁量边界、一次性使用/持续状态、对外可见时点”单行行为合同；不可用一个复杂 RoleHandler 工厂代替。特别检查官方人数配置（5–15）、男爵人数修正、NGJ 6 人剧本特殊容量、邪恶互认/恶魔掩饰、酒鬼真实/展示身份及夜序。

优先交互矩阵（可增加，不可无理由省略）：
- 投毒者 → 僧侣/士兵/市长 → 小恶魔：按动作当时的有效性结算保护与死亡；
- 投毒者死亡/中毒解除 → 尚未行动角色与已经行动角色：只影响未来，不能倒改历史；
- 小恶魔杀普通待行动角色 → 自动跳过；杀守鸦人/贤者 → 符合条件时生成死亡触发；
- 小恶魔自杀或死亡 → 猩红女巫/其他继承，人数/状态条件与新身份私密通知；
- 共情者邻居死亡、女仆是否真的因能力醒来、送葬者是否有前日执行；
- 占卜师红鲱鱼、间谍/陌客可选登记、醉毒虚假信息/实际公布；
- 白天处女提名、投票/鬼票、杀手、圣徒、市长、呆瓜，及胜负优先级；
- 5/6/7/9/10/12/13/15 人完整轨迹边界，其余人数开局覆盖；两内置剧本跨角色组合。
  
**正确性优先**：不穷举所有人数/座位/状态排列；用官方语义、角色覆盖表、代表性交互、完整回归与真机对局证明关键性质。还未写完的确定性信息函数不能伪装为已自动完成，待相应阶段以小而可验证的函数重建；不得恢复旧泛用候选引擎。

## 5. 代码归属与严格依赖方向

```text
Android UI / platform adapter      existing AI recommendation
       |                                     |
       +------------> narrow Host API <------+
                            |
                Script + nextStep(Session)
                            |
                 one Session / GameState
                     + ordered events
                     + one pending
                     + minimal mechanics
                     + atomic persistence
```

- UI 只管展示和收集真实输入；不决定角色是否唤醒/跳过、死亡、保护、胜负、不拥有单独的夜间业务游标真相。
- AI 只建议/裁量，不直接改正式事实；MANUAL/ASSISTED/AUTOMATIC 通过同一 Session 接受/提交接口。
- Script 只给元数据/夜序和少量脚本例外；Host 对确定状态转移负责。不引入通用规则语言、第二独立 Rules 权威、通用依赖图或按角色分层的 Handler 注册表。
- PlayerCard、GameSnapshot、UI checkpoint、夜末预览、恢复/复盘、AI strategy 必须是单向只读适配或删去，不得独立写 game truth。
- 包/源文件目标：职责内聚、单向引用、所有源码遵守既定 **<= 50,000 bytes/文件** 上限；禁止机械拆成大量一函数一文件。测试要验证行为，不绑旧类名。
