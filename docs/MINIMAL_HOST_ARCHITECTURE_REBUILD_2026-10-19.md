## 1. 产品目标与不可改变的边界

- 两项现行业务职责：**Host Core** 和 **现有 AI 推荐**。Host 在没有 AI/人工说书人帮忙决定流程的情况下，能够确定剧本、轮次和当前事实所规定的**下一可执行步骤**，以及唯一确定的机械结果。玩家作出的选择仍必须由玩家输入；规则确有裁量空间时由 AI 或人工说书人选择，不允许 Host 随意编造。
- 只有 **一个可写 Session / GameState**：座位、实际/展示身份、阵营、醉毒/保护/生死、角色变化、阶段、玩家操作、单一顺序事件与实际公布信息。UI、AI、复盘、对局恢复、读模型均不得成为第二事实权威。
- Script 定义固定夜序、角色和必要剧本特例；Host 从 **Script + 当前 Session + 有序已确认事件** 得到当前步骤。没有第二套可写游戏状态、通用世界枚举、候选合法域、评分或隐式 UI 裁定。
- **确定性规则由 Host 计算、执行并验证**，包括夜间条件唤醒/跳过、攻击是否致死、保护/中毒时间效力、死亡触发、角色继任、白天提名投票、胜负及无歧义真实线索。只有规则真正存在多个许可结果，才请求 AI/人工裁量；保留必要狭窄的结构/规则边界检查，禁止恢复旧通用 veto 引擎。
- **实际给角色展示的私密信息不可静默撤销**：记录实际数字、布尔、身份、配对、接收者及发生时点，即便真实说书人误播。Host 不为机械死亡重复合成公开信息观察。
- **死亡即时生效、夜末直接进入白天**：一旦确认，`Death` 即写入唯一 Session 并影响后续夜间角色；最后一步后 `NIGHT → DAY`，白天页面只读显示该夜已发生的死者。不设置独立 `DAWN` 阶段、专用播报页、二次 `PUBLIC AliveAt` 死亡观察或公开确认事务。UI 不得在夜间向玩家泄漏魔典私密信息。
- 现行两内置剧本 **Trouble Brewing（5–15 人）与 No Greater Joy（5–6 人）** 必须继续可玩；开局角色阵容防重复与同一玩家连续角色轮换两项均保留。未来自定义/Homebrew/动态剧本非当前要求；可删除其额外复杂性，但必须保留两内置剧本及所需解析。
- **保护现有 AI 整链**：首夜全局联合规划、后夜增量、提示词/API/解析、战略记忆、MANUAL/AI_ASSISTED/AI_AUTOMATIC、预选与逐项应用。不得为旧 Host 合法域或候选接口的保留牺牲最小 Host，也不得删除实际 AI 功能。API 付费实验须另行明确批准。
- Android CampHost 与以后 WebHost/EvidenceLab 只需共享状态和事件**语义合同**，不复制 Android UI 或旧存档/恢复技术；不可为了未来扩展先建设庞大通用引擎。

## 2. 夜间只前进、按步骤立即提交与安全恢复（2026-10-20 最终裁定）

**取代此前所有 Pending/Previous 设计，包括仅恶魔禁退的中间方案。** 这一新裁定适用于首夜和后夜所有角色：投毒者、僧侣、管家、恶魔、信息展示与其他角色。

1. 当前角色界面内选择目标/要展示的内容时，允许修改**当前未确认的 UI 草稿**。行动类点击 Next 立即原子提交；信息类可以反复全屏预览和返回原角色，**唯独点击 Next** 时提交最后一次确认预览的信息 Observation 并进入后继步骤。**没有额外的“开始当前步骤”按钮或交接页。**
2. **整个夜间流程不提供“上一步”**，无论该角色是行动类还是信息类；确认后的动作、选择和已实际展示的信息均不得通过常规导航修改、重复生成不同结果或撤销。已发布信息若需在当下再次看，必须重用已记录的同一事实而不能二次发布或变更；不得恢复跨角色 Back。
3. 删除夜间 `pendingOperation`、暂存/消费方法、步骤开始交接 UI、仅服务回退的预览与测试。**不建设 Undo/Redo、事件回滚、第二份 GameState**。普通 UI 选择草稿不等于 Session 中的第二游戏对象。
4. 投毒者点击下一步时 `Poison` 及中毒状态立即生效；随后僧侣即使被投毒，也正常选择对象，但保护会按真实投毒状态判定无效。僧侣、管家也在自己的 Next 时提交。恶魔同理：确认袭击即记录 `Attack`，对于无歧义结果当场更新 `Death` 和 GameState；士兵/有效僧侣保护不会死亡，市长转移/恶魔自杀继任须留在真实裁量步骤解决。
5. 夜间 `Death` 是已确认机械事实，发生时立即改变存活状态；之后的普通角色根据更新后的存活状态跳过，Ravenkeeper/Sage 等夜死触发根据已确定事实唤醒。夜晚结束直接进入白天，已有白天页面显示本轮真实死者；**不再创建黎明/公开死亡操作或再次选择死者、毒延续与继任**。
6. 需要稳定步骤身份和幂等确认：用户双击 Next 或界面重组不得重复记录同一事件；再进已确认步骤时不同目标直接拒绝。对局意外中断后恢复到**安全的未执行下一步**，优先保证能继续对局，不追求逐像素还原，更不回滚已发生的真实事件。
7. 真正的说书人口误或现实中已经展示错误信息，将来只能追加明确纠错记录，不能以返回按钮篡改历史。已有真实 AI 推荐与 MANUAL/AI_ASSISTED/AI_AUTOMATIC 三模式均应沿同一提交入口；未确认选择变更必须使过时建议失效。
8. **A（无准备页）**：首夜/后夜从已完成的上一个真实步骤直接呈现下一个真正可执行角色；删除 StartNight/ReadyCard/nightStarted 流程布尔/空操作。酒鬼、红鲱鱼、恶魔伪装等若尚未确认，是有事实的实际配置输入而不是通用准备页面。
9. **B（方桌日结）**：同一个白天方桌的一次确认即接受本日处决或无人处决、特殊效果、胜负；删除独立 EndConfirm/ExecutionConfirmScreen 路由及专属测试，不在别处再追加二次确认。
10. **C（死亡触发呆瓜）**：NGJ 呆瓜从已确认 Death/Execution、实际身份和是否已经执行选择的历史导出待处理角色动作；不得为“得知死亡”创建额外 ActionFact/Session 事实。保留真实玩家选座位及结果记录，保证夜死在白天展示后才走玩家输入。
11. **D2（信息最终确认）**：展示按钮只打开可返回的全屏预览；返回后高亮预览内容但**不提交、不推进**，说书人可再选择其他信息并预览。唯独本角色 Next 才将**最后确认的一条** Observation 作为唯一正式事件并推进；中途预览版本无正式记录；崩溃时未提交本步可直接重新选择/展示。不要持久记录 UI 草稿，Next 后幂等、不能回上一角色。

**实施范围说明（2026-10-20 最新）**：#335 已实现 Poison/Monk/Butler/Imp 单步提交与全夜无后退、Mayor 死亡转移、Imp 自杀及 Scarlet Woman 继任的即时 Session 原子事件。旧夜末自由选择死亡、继任和中毒延续的 UI、Session 接口及旧测试已在 `712d46e6` 删除。`0e63d9c` 删除独立 Dawn 阶段、播报页面与自动生成的二次 `PUBLIC AliveAt`，夜间最后的 Next 直接进入 Day，白天方桌显示已经死亡的玩家。`64c57df` 清理旧继任重复写入、更新 R2 守卫。`ccaef940` 修复 PhaseAdvance 时点清理临时夜间目标，并由[完整 Android CI #39349210480](https://github.com/Jazz0006/CampBoardGameHost/actions/runs/39349210480)及[R2 #39349210477](https://github.com/Jazz0006/CampBoardGameHost/actions/runs/39349210477)通过；旧预测 Adapter、完整 TB/NGJ 角色覆盖和中断恢复仍未完成。

## 3. 整局执行合同

开局：选内置剧本、5–15/NGJ 5–6、人数配置与剧本修正、选阵容/座位/真实及展示身份、酒鬼、必要红鲱鱼/恶魔掩饰。两类跨局多样性保留；首夜 AI 可提前规划但不能以建议充当事件。

第一夜：Host 根据首夜剧本顺序和当前身份生成开场邪恶信息、角色动作/私密信息；酒鬼按展示身份安排体验但不拥有镇民能力；无需唤醒时不额外要求人或 AI 判断。5–6 人与 7+ 人开场信息差异由剧本/人数决定。

后续夜晚：固定剧本夜序 + 玩家真实/展示身份 + 当前当夜有效能力 + **有序事实** 推出可执行动作。死亡、保护、投毒、失效、恶魔继任必须影响发生之后的角色，但不能按最终状态倒推修改之前已发生的信息；守鸦人/贤者是事件触发步骤，不能只靠当前存活角色集合过滤。间谍正常步骤展示已有方桌，不重建特殊魔典页面。

夜晚至白天：夜间最后一项实际步骤直接提交 `NIGHT→DAY`。白天方桌只读展示上一夜真正发生的死亡，不再让说书人按第二套死亡结果确认；NGJ 呆瓜等在得知死亡后必须作出的**真实角色行动**由白天流程直接处理，绝不作为独立黎明阶段。保密仍由界面和唯一 Session 的信息读取边界保证。

白天：自由讨论由人主持进度，但真实提名、投票、鬼票、最高票、处女触发处决、杀手行动、艺术家问答、白天正式处决和胜负判断共用一个 Session 事件与结算机制；Host 计算唯一结果，不把实际自由裁量和技术验证混为一谈。必要玩家输入仍由玩家作出。**不再导航至单独的“结束白天/确认处决”页：在现有方桌一次确认提交本日结果。** 呆瓜死亡的待执行选择从已发生的死亡及真实身份自动得出，不能新增“得知死亡”事件。

循环：每个正式机械变更后检查游戏终结与特殊继续条件，否则继续下一夜；不能维护日夜两个独立状态机。

## 4. 角色覆盖合同与非穷举组合矩阵

P0 必须依据两内置剧本官方/现存角色定义，制作**每个实际角色**“触发条件、必要玩家输入、确定效果、非唯一裁量边界、一次性使用/持续状态、对外可见时点”单行行为合同；不可用一个复杂 RoleHandler 工厂代替。特别检查官方人数配置（5–15）、男爵人数修正、NGJ 6 人剧本特殊容量、邪恶互认/恶魔掩饰、酒鬼真实/展示身份及夜序。

优先交互矩阵（可增加，不可无理由省略）：
- 投毒者 → 僧侣/士兵/市长 → 小恶魔：按动作当时的有效性结算保护与死亡；
- 投毒者死亡/中毒解除 → 尚未行动角色与已经行动角色：只影响未来，不能倒改历史；
- 小恶魔杀普通待行动角色 → 自动跳过；杀守鸦人/贤者 → 符合条件时生成死亡触发；
- 小恶魔自杀或死亡 → 猩红女巫/其他继承，人数/状态条件与新身份私密通知；
- 共情者邻居死亡、女仆是否真的因能力醒来、送葬者是否有前日执行；
- 占卜师红鲱鱼、间谍/陌客可选登记、醉毒虚假信息/实际公布；
- 白天处女提名、投票/鬼票、杀手、圣徒、市长、呆瓜，及胜负优先级；
- 5/6/7/9/10/12/13/15 人完整轨迹边界，其余人数开局覆盖；两内置剧本跨角色组合。
  
**正确性优先**：不穷举所有人数/座位/状态排列；用官方语义、角色覆盖表、代表性交互、完整回归与真机对局证明关键性质。还未写完的确定性信息函数不能伪装为已自动完成，待相应阶段以小而可验证的函数重建；不得恢复旧泛用候选引擎。

## 5. 代码归属与严格依赖方向

```text
Android UI / platform adapter      existing AI recommendation
       |                                     |
       +------------> narrow Host API <------+
                            |
                Script + nextStep(Session)
                            |
                 one Session / GameState
                     + ordered events
                     + confirmed actions
                     + minimal mechanics
                     + atomic persistence
```

- UI 只管展示和收集真实输入；不决定角色是否唤醒/跳过、死亡、保护、胜负、不拥有单独的夜间业务游标真相。
- AI 只建议/裁量，不直接改正式事实；MANUAL/ASSISTED/AUTOMATIC 通过同一 Session 接受/提交接口。
- Script 只给元数据/夜序和少量脚本例外；Host 对确定状态转移负责。不引入通用规则语言、第二独立 Rules 权威、通用依赖图或按角色分层的 Handler 注册表。
- PlayerCard、GameSnapshot、UI checkpoint、夜末预览、恢复/复盘、AI strategy 必须是单向只读适配或删去，不得独立写 game truth。
- 包/源文件目标：职责内聚、单向引用、所有源码遵守既定 **<= 50,000 bytes/文件** 上限；禁止机械拆成大量一函数一文件。测试要验证行为，不绑旧类名。
