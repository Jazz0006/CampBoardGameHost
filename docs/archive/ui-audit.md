# 血染钟楼说书人助手 UI 审计

**版本：0.2｜2026-07-23**  
**审计对象：Android 真机当前版本｜截图尺寸：1080 × 2400**

## 2. 总体结论

当前版本的业务流程已经可辨认，但界面仍属于功能原型。主要风险不是装饰不足，而是关键操作随页面滚动、敏感信息暴露、信息层级不稳定，以及危险操作缺乏明确区分。

第一轮重设计应优先解决：

1. 夜间行动单屏化与底部操作栏固定。
2. 玩家身份及说书人信息的防泄密。
3. 白天、提名、投票和处决的阶段层级与操作反馈。
4. 统一设计变量、按钮、卡片、选择状态和危险状态。
5. 首页、恢复和异常状态的补全。

## 3. 跨页面问题

### P0：必须在核心页面重设计时解决

#### 3.1 关键操作经常位于首屏之外

座位管理、提名、杀手行动等页面需要长距离滚动才能找到下一步。主持人边走动、单手操作时容易失去当前任务，也不符合“主操作始终可见”的验收要求。

**建议：**

- 在夜间行动、提名、投票、处决和特殊能力页面使用固定底部操作栏。
- 底部操作栏只保留一个主操作，并提供明确的返回或取消。
- 为 Android 导航栏和 iPhone 安全区预留空间。

#### 3.2 夜间页面暴露完整角色信息

夜间行动面板下方继续显示玩家角色列表。说书人将手机递给玩家或玩家从侧面看到屏幕时，可能泄露其他玩家身份。

**建议：**

- 夜间行动期间默认隐藏完整魔典和角色列表。
- “展示给玩家”进入独立的安全展示模式，只保留该玩家应看到的信息。
- 从后台恢复时先显示中性遮罩，不直接恢复到身份内容。

#### 3.3 阶段标题和进度会随滚动消失

提名、杀手行动和进入白天截图中，页面顶部的阶段信息已经部分或完全离开视口。说书人无法持续确认当前天数、阶段和目标。

**建议：**

- 使用紧凑且可吸顶的阶段栏。
- 持续显示天数或夜数、当前阶段和必要的步骤进度。
- 避免重复显示多个同义标题。

#### 3.4 危险操作没有危险视觉

“确认处决”“结束白天”“新游戏”等操作仍使用普通绿色或普通文字样式，和继续流程的主操作过于接近。

**建议：**

- 处决、结束游戏、清除数据使用暗红色危险按钮。
- 处决和结束游戏必须二次确认，并清楚显示目标和后果。
- “新游戏”不能作为无保护的普通页头文字操作。

### P1：建立设计系统时解决

#### 3.5 视觉方向与产品定位不一致

当前主要采用浅米色背景和绿色按钮，整体接近通用表单工具，尚未形成“高级、神秘、克制的夜间主持工具”辨识度。

**建议：**

- 按设计草案采用深色背景、炭灰表面、象牙白文字、黄铜金主操作和暗红危险状态。
- 只在首页、恢复和游戏结束页面使用较强的钟楼、月光或徽章元素。
- 功能页面保持低装饰、高对比。

#### 3.6 组件层级不稳定

页面同时出现多种卡片底色、边框按钮、绿色填充按钮和黄色说明框，但其语义并不始终一致。部分次要操作与主要操作尺寸接近。

**建议：**

- 统一 Primary、Secondary、Text 和 Danger 四种按钮。
- 统一信息卡、任务卡、选择卡、结果卡和折叠记录组件。
- 同一页面最多一个最突出的 Primary 按钮。

#### 3.7 辅助文字对比度偏低

浅灰文字在浅色背景上对比不足，低亮度和走动场景下可能难以快速读取。

**建议：**

- 主要文字和次要文字使用设计变量控制，不再使用任意灰色。
- 正文保持 16–18 px，元信息不低于 13–14 px。
- 使用真实手机最低亮度验证。

### P2：全流程推广时解决

#### 3.8 中英文混用

游戏结束弹窗中的 `Back` 和 `Play Again` 与中文界面不一致。

**建议：**

- 所有界面文字进入统一国际化资源。
- 中文模式显示“返回”和“再来一局”。
- 使用英文长角色名和长玩家名进行截断测试。

#### 3.9 游戏记录占用首屏空间

几乎每个游戏阶段都在主任务下方展开或露出“游戏记录”，使当前操作和历史信息竞争注意力。

**建议：**

- 默认折叠游戏记录，只显示条数和最近的重要事件摘要。
- 历史记录作为次级抽屉或独立页面。
- 当前阶段完成、跳过和冲突仍需立即反馈。

## 4. 页面级审计

### 4.1 座位管理

**观察：**

- 圆桌能直观表达顺序，但玩家姓名出现贴边、遮挡和视觉拥挤。
- 页面同时承担座位调整、候补玩家和游戏选择，任务过多。
- 选择游戏及后续按钮位于较深的滚动位置。

**建议：**

- 将流程拆为“选择玩家与座位”以及“选择游戏”两个步骤。
- 圆桌节点只显示号码和截断后的姓名，选中后显示完整信息。
- 在固定底栏显示“继续选择游戏”。

### 4.2 剧本配置

**观察：**

- 信息清楚，但页面上半部拥挤、下半部留白过多。
- “开始发牌”过早承担不可逆操作的感觉，缺少配置确认摘要。

**建议：**

- 将剧本、玩家人数、角色分布和特殊规则做成一张确认摘要。
- 主操作改为更明确的“确认配置并开始发牌”。

### 4.3 身份展示

**观察：**

- 单屏内容集中，身份是第一视觉层级。
- 大面积空白可用于加强私密展示提示和遮挡操作。
- 当前没有明显的“按住查看”或防误触机制。

**建议：**

- 进入页面先显示中性封面，按住或滑动后才显示身份。
- 松手或交给下一位后立即重新遮罩。
- 角色能力保持清晰，避免装饰性字体影响阅读。

### 4.4 说书人准备

**观察：**

- 推荐方案、修改裁定、夜晚开始和游戏记录同时争夺注意力。
- 推荐区域信息密度高，夜间开始入口位于页面中部。

**建议：**

- 把推荐方案作为可折叠的准备步骤。
- 确认后进入独立的“夜晚即将开始”页面。
- 当前页面只保留一个明确的下一步。

### 4.5 夜间行动

**观察：**

- 夜数、阶段、步骤和当前玩家已经存在，是良好基础。
- 交互型步骤的玩家按钮列表使页面明显变长。
- “上一步”和“完成，下一步”未固定。
- 完整角色信息位于下方，存在泄密风险。

**建议：**

- 作为第一优先级页面重做。
- 顶部固定夜数和进度，中部只显示当前玩家、角色、单句指令和必要选择。
- 底部固定“上一步 / 确认并继续”。
- 详细规则、历史记录和魔典放入折叠层或独立入口。

### 4.6 给玩家的展示信息

**观察：**

- 已经使用独立的深色全屏展示页，没有同时显示说书人备注、完整魔典或其他玩家身份，安全方向正确。
- 角色信息、说明和结果位于屏幕中央，适合将手机短暂展示给目标玩家。
- `5 2` 只依靠数字和前文表达两名候选玩家，信息关系不够直观。
- “关闭展示卡”按钮的文字与背景对比度过低，在真机截图中接近不可见。
- 顶部状态栏和底部 Android 导航栏仍为亮色，与展示页割裂，也会在昏暗房间中产生明显亮边。
- 页面没有明确显示自动隐藏、按住查看或返回后台后的遮罩机制。

**建议：**

- 保留独立安全展示模式，禁止在此页面渲染隐藏答案、说书人备注、其他角色或游戏记录。
- 将候选玩家显示为明确的座位标签，例如“5号”和“2号”；必要时可加入姓名，但不能加入真实身份。
- 提高关闭按钮的文字、边框和背景对比度，保证可识别且触控区域至少为 48 × 48 px。
- 展示模式使用深色系统状态栏和导航栏，条件允许时启用沉浸式全屏。
- 增加“按住显示，松手遮罩”或短时自动隐藏机制；切到后台和重新进入应用时必须先显示中性遮罩。
- 关闭后回到当前夜间步骤，并保留已完成的选择，不得重置流程。

### 4.7 进入白天

**观察：**

- “昨晚死亡”和进入白天的主操作较清楚。
- 页面顶部阶段标题已经滚出视口。
- 历史记录紧接主卡片，削弱天亮信息。

**建议：**

- 将天亮宣布做成短暂的独立总结页。
- 明确列出死亡、无人死亡或特殊异常。
- 主操作固定在底部。

### 4.8 白天管理

**观察：**

- 存活人数、处决门槛和最高票信息有价值。
- “开始提名”“杀手行动”“结束白天”尺寸相近，危险性和主次不够清楚。

**建议：**

- “开始提名”为主操作。
- 特殊能力放入次级操作区，并显示是否已使用。
- “结束白天”使用低频危险操作样式并二次确认。

### 4.9 提名

**观察：**

- 提名人与被提名人使用两个完整玩家列表，页面长度翻倍。
- 选中状态主要依赖绿色填充。
- “开始投票”只有滚动到底部才能看到。

**建议：**

- 采用两步选择：先选提名人，再选被提名人。
- 选中状态同时使用勾选图标、文字和颜色。
- 顶部持续显示“提名人 → 被提名人”摘要。
- “开始投票”固定在底部，未完成选择时禁用并说明原因。

### 4.10 投票

**观察：**

- 门槛、票数和结果都清楚。
- 加减按钮可用，但缺少投票顺序和每位玩家投票权状态。
- 达到门槛后“继续提名”仍使用主按钮，可能掩盖当前最高票已变化。

**建议：**

- 明确显示候选人、门槛、当前票数和是否成为最高票。
- 为死亡玩家亡者票和无投票权状态预留组件。
- 提交票数后给出明确结果反馈，再允许继续提名或结束白天。

### 4.11 处决

**观察：**

- 目标、票数和确认问题已经明确。
- “确认处决”仍为普通绿色按钮，危险等级不足。
- 最高票信息在窄宽度下发生不自然换行。

**建议：**

- 使用暗红 Danger 按钮和确认弹窗。
- 重要数字与玩家姓名使用结构化行布局，避免文本自然换行破坏信息关系。
- 确认前清楚显示处决可能立即触发的胜负检查。

### 4.12 杀手行动

**观察：**

- 声称者和目标分组清楚。
- 两组玩家列表加说明文字导致页面很长，结算按钮不一定始终可见。
- 特殊规则说明与操作控件混在同一视觉层级。

**建议：**

- 使用两步选择和固定结算按钮。
- 规则说明默认折叠，只显示一句结果影响摘要。
- 明确显示能力仅可使用一次以及已经声称过的玩家。

### 4.13 游戏结束

**观察：**

- 胜利阵营、原因和角色表均已提供。
- 系统式弹窗缺少游戏结束的仪式感。
- 内容较长，按钮使用英文且位于弹窗底部。
- 背景仍显示未结束的白天管理页面，视觉状态不彻底。

**建议：**

- 改为独立游戏结束页，而非普通弹窗。
- 突出胜利阵营、胜负原因和关键事件。
- 完整角色表和游戏记录放入可展开区域。
- 使用中文“返回首页 / 再来一局”，并区分主次操作。

## 5. 重设计优先级

建议继续采用既定页面顺序：

1. 夜间行动。
2. 白天玩家状态与白天管理。
3. 首页与恢复游戏。
4. 游戏配置。
5. 提名、投票和处决。
6. 夜间总结。
7. 游戏结束。

## 6. 下一步交付物

当前截图已足够进入视觉方向与设计系统阶段。下一步应：

1. 建立 `ui/design-tokens.css`。
2. 创建 `ui/ui-showcase.html`，覆盖按钮、玩家选择、状态标签、阶段栏、夜间行动卡、固定底栏、弹窗、Toast、空状态、错误状态和加载状态。
3. 用同一设计系统制作夜间行动、白天玩家状态和首页三个关键页面原型。
4. 在 375 × 812 与 390 × 844 视口检查。
5. 原型确认后，再补拍缺失页面并在 Android Chrome 与 iPhone Safari 真机复核。
