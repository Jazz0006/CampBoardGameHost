## 1. 目标与边界

本设计解决两个已经出现、且会在后续内容扩展中迅速放大的架构问题：

1. Blood on the Clocktower 不能继续把 Trouble Brewing 当作代码中的唯一结构；应用需要支持 Trouble Brewing、No Greater Joy、Bad Moon Rising、Sects & Violets，以及后续官方/自定义剧本。
2. 狼人杀不能继续通过 `playerCount + includeSeer/includeWitch/includeHunter` 和固定 JudgeStep 表达所有板子；新的角色组合不应要求修改 Host UI 和流程主干。

本设计的核心原则是：

> **Script / Board 只组合角色；Role / Character Registry 定义角色能力与交互元数据；FlowPlanner 根据当前状态、实际在场角色和事件动态生成下一步 HostInteraction。**

它不是一个“万能桌游规则 JSON DSL”，也不替代现有的 Possible Worlds、动态推荐、持久化或规则正确性规范。

职责关系如下：

```text
Script / Board Definition
        ↓
Role / Character Registry
        ↓
Validated Game Content
        ↓
FlowPlanner
        ↓
HostInteraction / DecisionPoint
        ↓
Dynamic Decision Engine / Rule Handler
        ↓
Committed Action / Observation / Event
        ↓
Game State
        └──────────────→ FlowPlanner recompute
```

## 2. 为什么现在设计、但不能现在实施

当前分支仍处于 Phase A remediation：R2 是严格 behavior-preserving 的 MainActivity mechanical decomposition，之后还有 R3 validation contract、R4 A4.5 lifecycle hardening 和 R5 Phase A re-exit。

因此当前阶段只能做到：

- 冻结目标架构；
- 在 R2 拆文件时避免新建更深的 Trouble Brewing / Werewolf hardcode；
- 给 R6 明确上游输入边界；
- 不修改当前用户可见流程、存档 schema、规则行为或推荐输出。

正式实施插入为：

```text
R2 MainActivity mechanical decomposition
  ↓
R3 A2/A3 validation contract
  ↓
R4 A4.5 lifecycle hardening
  ↓
R5 Phase A re-exit
  ↓
R5.5 Script & Dynamic Flow Foundation   ← 本文
  ↓
R6 revision-driven dynamic decision engine
```

原因是：如果先做 R6，再做多剧本，R6 很容易把 Trouble Brewing 的角色表和夜序固化到 decision-point 生成逻辑；但如果在 R2 直接实现本设计，又会破坏当前 correctness-remediation 的范围控制。

## 3. 当前代码中的可复用基础与迁移债务

### 3.1 已存在且应保留的 Ruleset 基础

当前已经存在：

```text
app/src/main/assets/rules/trouble_brewing.json
RulesetJsonLoader.kt
RulesetKnowledge.kt
RulesetRef.kt
```

其中 `RulesetRef` 已具备：

```text
scriptId
scriptContentHash
rulesetVersion
sourceRevision
coverage = VERIFIED / PARTIAL / UNVERIFIED
```

这是正确方向。R5.5 应扩展这条 seam，而不是创建第二套 script identity。

### 3.2 当前 `trouble_brewing.json` 的问题

当前 JSON 同时承担：

```text
character ability text
+ script composition
+ first-night order
+ other-night order
+ jinxes
```

单剧本时可以工作，但扩展到多个剧本会产生：

- 相同角色定义在多个 script 中重复；
- 文案修正需要同时更新多个 script；
- 角色行为与剧本组合边界模糊；
- custom script import 很难判断“角色定义”和“剧本选择”谁是权威；
- hash/version 的语义不清晰。

R5.5 必须把“角色目录”和“剧本组合”规范化为不同对象。

### 3.3 当前 Werewolf 的 hardcode

当前 `WerewolfGameSupport.kt` 的模式仍相当于：

```kotlin
data class WerewolfTemplate(
    playerCount,
    werewolfCount,
    includeSeer,
    includeWitch,
    includeHunter,
)
```

并使用固定：

```text
Wolves → Seer → Witch → Hunter → Dawn → DayVote
```

这只是把旧逻辑从 MainActivity 抽到了独立文件，并没有形成可扩展的板子系统。R2 必须保持它行为不变；R5.5 再迁移。

## 4. 外部项目中采用的设计经验

### 4.1 `Jazz0006/my-game-host-vibration`

该项目已经验证了一条适合复用的原则：

> A script selects roles and counts for a concrete table setup. Role behavior remains in the role registry; scripts only compose roles.

其结构值得直接借鉴：

```text
WerewolfScriptDefinition
    id / name / roleDeck

RoleDefinition
    id / team / nightOrder / interaction / hooks

WerewolfNightPlanner
    GameState + RoleRegistry
        → filter active interactions
        → sort by registered night order
        → produce current interaction
```

本项目不复制 TypeScript 代码，但采用同一职责划分。

### 4.2 官方 BotC custom script JSON

外部交换格式优先兼容 The Pandemonium Institute 当前 custom-script 生态，而不是发明完全独立的文件格式。

需要支持的关键概念包括：

- script 中以官方 character ID 组合角色；
- `_meta` 元数据；
- homebrew character object；
- `firstNight` / `otherNight` 顺序元数据；
- reminder、setup、jinx、special 等角色元数据；
- meta-level night-order override；
- `dusk`、`minioninfo`、`demoninfo`、`dawn` 等系统步骤。

外部 JSON 是 **interchange format**，不是内部运行时领域对象。

### 4.3 `tchajed/botc-tools`

值得借鉴的模式是：

```text
ScriptData holds character IDs
        ↓
resolve IDs through central role catalog
        ↓
derive night order from character metadata
        ↓
script-specific override only where needed
```

这与本项目已有 `RulesetRef` 可以自然组合。

### 4.4 外部参考的使用边界

这些项目用于架构参考，不作为规则权威。规则权威顺序仍由 v2.2 决定：

```text
Official role text / Almanac / published ruling
> project reviewed golden expectation
> external executable oracle
> external implementation/research
> current production behavior
```

## 5. BotC 内容模型

### 5.1 外部格式与内部格式分离

正式管线：

```text
Official/custom Script JSON
        ↓
ScriptJsonParser
        ↓
ScriptNormalizer
        ↓
ClocktowerScriptDefinition
+ CharacterRegistry
        ↓
ScriptValidator
        ↓
ValidatedClocktowerRuleset
```

禁止让 UI、FlowPlanner、PlayerWorldSet 直接读取原始 JSON Map。

### 5.2 `CharacterDefinition`

概念模型可等价于：

```kotlin
data class CharacterDefinition(
    val id: RoleId,
    val nameKey: String,
    val team: CharacterTeam,
    val edition: String?,
    val abilityTextKey: String,
    val firstNightOrder: Int?,
    val otherNightOrder: Int?,
    val firstNightReminder: String?,
    val otherNightReminder: String?,
    val reminders: List<String>,
    val setupMetadata: SetupMetadata,
    val jinxes: List<JinxRef>,
    val special: List<SpecialMetadata>,
    val behaviorKey: String?,
    val automationCoverage: RuleCoverage,
)
```

具体字段可以随正式 schema 调整，但必须满足：

- stable RoleId 是领域身份；
- 本地化显示名不是身份；
- script 不复制完整 character definition；
- behaviorKey / handler binding 不允许由 ability 文本推断。

### 5.3 `ClocktowerScriptDefinition`

概念模型：

```kotlin
data class ClocktowerScriptDefinition(
    val id: ScriptId,
    val name: String,
    val author: String?,
    val characterIds: List<RoleId>,
    val firstNightOverride: List<NightOrderToken>?,
    val otherNightOverride: List<NightOrderToken>?,
    val source: ScriptSource,
    val contentHash: String,
)
```

Script 的职责是“选择哪些角色可用 + 少量 script-level override”，不是实现角色规则。

### 5.4 Character Catalog 与 Script Catalog

目标目录可等价于：

```text
clocktower/catalog/
  ClocktowerCharacterRegistry.kt
  ClocktowerScriptCatalog.kt
  ScriptJsonParser.kt
  ScriptNormalizer.kt
  ScriptValidator.kt
```

内置官方角色可以来自版本化 assets；运行时暴露强类型 catalog。

## 6. 不构建通用规则 JSON DSL

禁止把复杂角色规则表达为类似：

```json
{
  "trigger": "PLAYER_DIED",
  "condition": "...",
  "effect": "..."
}
```

并试图让通用解释器覆盖所有角色。

原因：BotC 中大量规则包含：

- registration；
- malfunction；
- storyteller choice；
- death prevention/redirect；
- resurrection；
- role succession/change；
- setup mutation；
- conditional win/loss；
- interaction-local hidden facts；
- information that may be arbitrary when malfunctioning。

把这些压成 DSL 会制造一个比 Kotlin 代码更难验证、更难类型检查、更难对 golden corpus 做回归的第二编程语言。

正确划分是：

```text
JSON / metadata
    composition, text, ordering, reminders, setup metadata,
    jinxes, import provenance, coverage

Kotlin handler / rules domain
    legal choices, rule resolution, state transition,
    registration, death/revival, role change, victory,
    epistemic semantics, storyteller recommendation
```

## 7. Character Handler / Role Handler

角色行为注册可以等价于：

```kotlin
interface ClocktowerCharacterHandler {
    val roleId: RoleId

    fun interactions(context: FlowContext): List<HostInteraction>
    fun legalChoices(context: RuleContext): LegalChoiceSet
    fun apply(choice: LegalChoice, state: GameState): RuleResolution
}
```

不要求每个角色都实现所有方法；正式实现可以拆成 capability interfaces / hooks。

推荐的 hooks 范围：

```text
onSetup
onPhaseStarted
beforeDeath
afterDeath
onExecution
onNomination
onNightActionResolved
onRoleChanged
resolveRegistration
evaluateVictory
```

这些 hook 必须保持尽可能纯函数化、可单元测试，并与 Compose/UI 分离。

## 8. Dynamic FlowPlanner

### 8.1 FlowPlanner 的职责

FlowPlanner 回答：

> 在当前游戏状态下，接下来有哪些合法/需要处理的 HostInteraction？

它不回答：

> 这些合法候选里，哪一个说书人选择最有趣？

后一个问题属于 dynamic decision/recommendation engine。

### 8.2 Clocktower 目标管线

```text
GameState
+ Current Script
+ Characters actually in play
+ CharacterRegistry
+ Pending Events
        ↓
ClocktowerFlowPlanner
        ↓
HostInteraction
```

FlowPlanner 至少组合三类来源：

1. **system interactions**：dusk、minion info、demon info、dawn、day/night transition；
2. **phase role interactions**：当前实际在场且该阶段有行动的角色；
3. **event-triggered interactions**：死亡、处决、角色变化、复活等事件产生的临时步骤。

### 8.3 夜序不是固定流程表

夜序的计算原则：

```text
script/meta override if explicitly present
else character registry firstNight/otherNight ordering
+ required system tokens
+ current-state eligibility
+ triggered interactions
```

因此“换一个 script”不应导致新增：

```kotlin
when (script) {
    TroubleBrewing -> ...
    BadMoonRising -> ...
    SectsAndViolets -> ...
}
```

### 8.4 waking 与 functioning 必须分开

Drunk/Poisoned 等状态经常意味着“能力不能正常产生效果”，但并不等价于“角色不应该被叫醒或不能进行选择”。

因此 FlowPlanner 的：

```text
should interaction exist / should player wake
```

与 Rules Engine 的：

```text
ability functioning / effect truth / legal storyteller output
```

必须是不同判定。

### 8.5 事件驱动流程

至少预留以下结构化事件：

```text
PHASE_STARTED
NOMINATION_STARTED
VOTE_RESOLVED
EXECUTION_PENDING
PLAYER_DIED
PLAYER_REVIVED
ROLE_CHANGED
NIGHT_ACTION_RESOLVED
DAY_ACTION_REQUESTED
```

例如：

```text
Imp attack resolves
  → PLAYER_DIED
  → if Ravenkeeper condition applies
  → enqueue Ravenkeeper HostInteraction
```

这比在固定 night step list 中预先塞入所有可能步骤更可靠。

## 9. `HostInteraction` 作为 UI 与规则之间的稳定投影

UI 不应知道“现在是 Poisoner、下一步是 Monk”并自己拼流程。

目标是 UI 只渲染：

```kotlin
data class HostInteraction(
    val id: InteractionId,
    val phase: GamePhase,
    val actorSeats: List<Int>,
    val roleId: RoleId?,
    val kind: InteractionKind,
    val promptModel: PromptModel,
    val completionPolicy: CompletionPolicy,
    val decisionPointId: String?,
)
```

具体字段可调整，但要求：

- UI 不通过 role-name `when` 决定下一个步骤；
- interaction ID 可进入 revision/replay/idempotency；
- 需要说书人决策的 interaction 才产生 dynamic decision point；
- 纯玩家动作和纯系统 transition 不被伪装成“推荐候选”。

## 10. 与 revision-driven dynamic decision engine 的边界

正式依赖方向：

```text
ClocktowerFlowPlanner
        ↓
open HostInteraction / StorytellerDecisionPoint
        ↓
DynamicDecisionSnapshotFactory
        ↓
LegalChoiceGenerator
        ↓
Epistemic / Narrative / Quality evaluation
        ↓
Coordinator / Committer
        ↓
ActionFact / Observation / State mutation
        ↓
ClocktowerFlowPlanner recompute
```

因此 R6 开始前必须保证：

- decision point 不再由 Trouble Brewing enum 或 UI hardcode 生成；
- R6 消费 script-aware 的 `ScriptId / RoleId / RulesetRef / FlowContext`；
- `nightOrderPosition` 可以是 replay/定位信息，但不能成为定义游戏流程的唯一事实；
- FlowPlanner 不负责 stale-generation、commit transaction 或 candidate scoring；
- Dynamic Decision Engine 不负责决定“有哪些角色该醒”。

## 11. 与 PlayerWorldSet / Possible Worlds 的边界

v2.2 已要求 `PlayerWorldSetIdentity` 包含 `ruleset identity`。该设计保持不变。

R5.5 只负责确保 normalized ruleset 能稳定产生：

```text
ScriptId
RulesetRef
RoleId set
ruleset content hash/version
```

PlayerWorldSet 继续负责：

- recipient perspective；
- legal possible worlds；
- observation filtering；
- registration semantics；
- exact/shadow cardinality；
- epistemic metrics。

禁止把 Script JSON 直接作为 PlayerWorldSet 的规则解释器。

## 12. Custom Script / Homebrew 的安全降级

现有 `RuleCoverage` 应成为正式安全边界：

### `VERIFIED`

角色/规则版本已由项目 handler + official/golden corpus 覆盖。

允许：

- 自动 FlowPlanner；
- 已验证范围内的 legal choice generation；
- 按 rollout policy 进入 AUTO/ASSISTED。

### `PARTIAL`

角色已识别，但某些能力或阶段未完整自动化。

允许：

- script 导入；
- 角色文本、reminder、夜序提示；
- 已验证的 interaction 自动化；
- 未覆盖部分明确 `MANUAL_ONLY` / manual resolution。

### `UNVERIFIED`

未知 homebrew 或当前实现没有可验证 handler。

允许：

- 显示角色文本和 script composition；
- 使用明确可解析的 metadata 做辅助排序/提示；
- 说书人手动确认和推进。

禁止：

- 根据自然语言 ability text 猜测规则；
- 静默当成 VERIFIED；
- 返回伪造的 AUTO correctness；
- 将“不认识该角色”解释为该 interaction 不存在。

## 13. Werewolf 多板子模型

### 13.1 BoardDefinition

目标概念：

```kotlin
data class WerewolfBoardDefinition(
    val id: BoardId,
    val name: String,
    val roleDeck: Map<RoleId, Int>,
    val options: WerewolfRuleOptions,
    val contentHash: String,
)
```

新板子如果只使用已有角色，应做到：

> 新增一份 board definition 即可，不修改 Host UI、JudgeStep 或 FlowPlanner 核心。

### 13.2 WerewolfRoleRegistry

角色定义类似：

```text
id
team
night-order metadata
interaction kind/mode
wake/completion policy
eligibility
pure hooks / rule handler
```

### 13.3 Board 与 house rule 分离

以下内容不应都塞进 board identity：

```text
角色组成
vs
遗言规则
女巫首夜自救规则
同守同救等桌规
投票/警长等模式开关
```

Board 主要描述角色组合；可独立变化的 house rule 进入 `WerewolfRuleOptions` 或等价配置，并参与 game/ruleset identity。

### 13.4 不与 Clocktower 强行共用一个 FlowPlanner

两种游戏可以共享：

```text
Variant/Script identity pattern
Role registry pattern
HostInteraction projection
Event/replay concepts
validation/coverage concepts
```

但保持独立：

```text
ClocktowerFlowPlanner
WerewolfFlowPlanner
ClocktowerCharacterHandler
WerewolfRoleHandler
```

禁止为了“通用”而构建一个充满 game-type `when` 的 `GenericBoardGameRuleEngine`。

## 14. Persistence 与 identity

### 14.1 新游戏必须固定内容身份

创建游戏时至少保存：

```text
scriptId / boardId
normalized content hash
rulesetVersion
sourceRevision / import provenance where applicable
role/character IDs actually assigned
relevant house-rule options
```

恢复旧游戏时不得只按“当前 catalog 中同名 script”重新解释历史。

### 14.2 deterministic normalization

同语义 script 的 canonical normalized representation 必须稳定，避免仅因：

- JSON whitespace；
- 无意义 object-key 顺序；
- import file name；
- localized display name；

导致新的 ruleset identity。

有语义的顺序（例如明确 night-order override）必须保留。

### 14.3 handler compatibility

content hash 只能证明内容相同，不能单独证明执行语义相同。长期需要让保存/回放能够识别：

```text
ruleset content identity
+ semantic/handler version
```

正式字段在 S4 migration 设计时冻结，禁止 R2 提前改 persistence schema。

## 15. R5.5 实施批次

### S0 — Schema / Catalog / Import / Validation

目标：建立纯数据与强类型 catalog，不改变现有游戏行为。

工作：

- CharacterDefinition / ScriptDefinition / BoardDefinition；
- central registries；
- official custom-script JSON parser + normalizer；
- deterministic content hash；
- validation errors；
- `RuleCoverage` 映射；
- 将现有 `RulesetJsonLoader` 能力迁移/适配到新 catalog，而不是并存第二套 loader。

退出条件：

- Trouble Brewing normalized 后与现有角色集合/夜序 metadata 等价；
- unknown ID / duplicate / invalid night token fail closed；
- JSON whitespace/key-order 不改变 normalized hash；
- 不改变任何生产 Host 流程。

### S1 — Trouble Brewing FlowPlanner golden migration

目标：以 TB 作为行为等价基线，把固定 night/day flow 迁到 `ClocktowerFlowPlanner`。

要求：

- legacy 与 planner shadow diff；
- first night / other nights / day transition golden parity；
- Poisoner/Monk/Imp/Undertaker/Ravenkeeper 等既有场景结果不变；
- 当前所有已提交 observation/action 的 replay 顺序不变。

退出条件：TB 行为 golden-equivalent 后才能关闭 legacy flow source。

### S2 — No Greater Joy second-script proof

目标：用已有第二剧本证明体系不是“把 TB hardcode 换了目录”。

要求：

- 使用同一 CharacterRegistry；
- ScriptCatalog 切换角色集合；
- 不新增 script-specific Host UI 分支；
- script change 会改变 RulesetRef/content identity。

### S3 — Werewolf BoardRegistry + FlowPlanner migration

目标：把当前 Classic template / fixed JudgeStep 迁移为 board + role registry。

要求：

- 现有默认板子行为等价；
- 新增只由现有角色组成的 board 不需要修改 Host UI；
- role-specific wake/action 来自 registry/planner；
- house-rule options 与 board composition 分离。

### S4 — Persistence/schema migration

目标：正式保存 variant/ruleset identity，并保证旧存档可显式迁移或拒绝。

至少覆盖：

- scriptId / boardId；
- content hash/version；
- handler/semantic compatibility identity；
- current role IDs；
- house-rule options；
- import provenance where needed。

禁止静默把旧 save 解释成最新同名 script。

### S5 — Regression / legacy removal / R6 handoff

完成：

- TB full golden regression；
- NGJ second-script proof；
- Werewolf default-board parity；
- restore/replay；
- invalid/partial/unverified import safety；
- remove/disable legacy script enum and fixed flow only after parity；
- 更新 R6 input contract。

R5.5 退出后，R6 才允许实现依赖新 flow source 的 production dynamic decision path。

## 16. R5.5 Definition of Done

必须同时满足：

1. 增加一个仅由已支持 BotC 角色组成的新 script，不需要修改 Kotlin flow core。
2. 增加一个仅由已支持狼人杀角色组成的新 board，不需要修改 Host Screen / fixed JudgeStep。
3. 增加新角色时主要增加 metadata + handler，而不是修改 FlowPlanner 主干。
4. UI 渲染 `HostInteraction`，不通过角色名称控制主流程。
5. Trouble Brewing 迁移前后 official/golden rule result 与合法夜序等价。
6. `ScriptId / BoardId / RulesetRef / content hash` 可稳定保存、恢复和 replay。
7. unknown homebrew 不会被系统猜测为 VERIFIED automation。
8. FlowPlanner 与 Dynamic Decision Engine 职责独立并有 contract tests。
9. PlayerWorldSet 继续通过 ruleset identity 隔离不同剧本，不读取 raw script JSON。
10. legacy hardcoded script/board flow 只有在 shadow parity 后才移除。

---

## 17. 内容扩展顺序

R5.5 是架构迁移，不是“顺便实现所有官方剧本”。推荐顺序：

```text
TB               golden migration baseline
↓
No Greater Joy   second-script structural proof
↓
R5.5 exit
↓
R6 script-aware dynamic decision engine
↓
Bad Moon Rising  first real stress-test content
↓
Sects & Violets
↓
official-format custom scripts / homebrew assisted mode
```

BMR 适合作为第一个大型内容压力测试，因为其死亡、保护、复活和条件触发比 TB 更能验证 event-driven FlowPlanner。但 BMR 内容实现不属于 R5.5 foundation 的退出前置。

---

## 18. R2–R5 期间的保护规则

在 R5 退出之前：

- 本文只作为未来架构约束，不作为扩大当前任务范围的许可；
- R2 可以把 hardcoded 函数机械移动到新文件，但不能“顺便”迁移为 registry/planner；
- R3/R4 不得为了未来多剧本改变 official golden expectation；
- 不改变 persistence schema；
- 不加入 BMR/S&V production content；
- 不让 R6 旧计划在 R5.5 之前提前恢复为 READY；
- 若当前拆分必须新增 seam，优先使用 `RoleId`、`RulesetRef`、纯函数接口，避免新增 `TroubleBrewing` 专用依赖。

## 19. 最终设计原则

1. Script/Board 组合角色，不承载完整可执行规则。
2. Character/Role Registry 是角色元数据与 handler binding 的单一入口。
3. FlowPlanner 从当前状态生成流程，不从固定剧本步骤表推进。
4. Flow planning 与 recommendation selection 是两个系统。
5. waking eligibility 与 ability functioning 分离。
6. 事件触发能力使用结构化 lifecycle hooks，而不是 UI 特判。
7. 外部 BotC JSON 优先兼容官方生态，但内部必须 normalize 为强类型对象。
8. 不从自然语言 ability text 推断自动规则。
9. VERIFIED / PARTIAL / UNVERIFIED 决定自动化安全等级。
10. Clocktower 与 Werewolf 共享架构模式，不强行共享同一个规则引擎。
11. script/board/ruleset identity 必须稳定、可持久化、可回放。
12. R5.5 先迁移架构，再增加 BMR/S&V 等大型内容。
13. R6 必须消费 script-aware FlowPlanner 的 decision point，不重新 hardcode Trouble Brewing。
14. 当前 R2–R5 correctness 路线优先级高于本设计的功能实现。
